# T46 · 会话编辑器 —— 设计方案

> 目标：在已有「会话迁移」之上，新增**会话修改**能力 —— 删除 / 新增 / 局部修改，
> 支持**覆写**与**新增**两种写入方式，支持**同账号**与**跨账号**，再把「修改后的会话」写回去。
>
> 范围（用户已确认）：**Trae + WorkBuddy 双侧** · **全字段可编辑** · **会话级 + 消息级都要批量删除** ·
> **跨客户端（Trae ↔ WorkBuddy）** · 编辑形态 **全部结构化表单** · 校验 **分级（硬拦 + 警告）** ·
> 关联表 **全部暴露**（含 `fts_*`） · 跨端写入 **复用现有导入链路**。

---

## 1. 为什么不能「重建会话」

Trae 的会话不是「一个标题 + 一串消息」，而是**一组按逻辑 id 相互引用的表**。改坏任意一处引用，
客户端的表现是「会话在但打不开 / 重启后消失 / 只剩一句」。已踩过的坑（见 `docs/任务书.md`）：

| 坑 | 后果 |
| --- | --- |
| 同库复制时 `session_id` 在循环外生成 | 整批共用一个 id ⇒ 只有第一条成功，其余静默丢失 |
| 按位置 zip 推断 `message_id` 映射 | `IN (...)` 走索引按字母序返回 ⇒ 与 rowid 序错位，消息错配 |
| 只改 `chat_session.project_id`，漏掉 `session_project` / `context.last_real_project_id` | 客户端删不掉 + 重启后复活 |
| 写库前不合并 WAL | 抹掉客户端刚写下、还没 checkpoint 的数据 |
| 用整库重写（`encrypt_db_file`）而不是增量回写 | 一次操作重写 8 万页 / 300+ MB |

**结论：编辑器的写入必须走「既有原语拼装」，不另写一套。**

## 2. 读模型（EditDoc）

一次读出一个会话的**全部相关行**，而不是只看 `chat_session`。

表集合的枚举沿用 `trae_delete::classify_tables()`（**不写死表名**，按列名判定）：

- **session 作用域**：含 `session_id` 列的表 → 用 `WHERE session_id = ?` 取行
- **message 作用域**：只含 `message_id` 列的表 → 用
  `WHERE message_id IN (SELECT message_id FROM chat_message WHERE session_id = ?)` 取行

读取入口走 `trae_export::reader_plain_path()`（快照 + 合并 WAL 的工作副本），**只读，绝不改库**。

```jsonc
{
  "clientKey": "trae-cn",
  "sessionId": "68f0a1b2c3d4e5f6a7b8c9d0",
  "title": "…",
  "tables": [
    {
      "name": "chat_session",
      "scope": "session",          // session | message
      "editable": true,
      "derived": false,            // fts_* 标记为 true（检索镜像）
      "columns": [ { "name": "session_id", "type": "TEXT", "notNull": true, "pk": true, "dflt": null } ],
      "rows": [ { "session_id": "…", "session_title": "…" } ]
    }
  ],
  "warnings": [ "…" ]
}
```

### 值的 JSON 映射（**必须可逆**）

| SQLite | JSON | 回写 |
| --- | --- | --- |
| NULL | `null` | NULL |
| INTEGER | number | INTEGER |
| REAL | number（带 `.`） | REAL |
| TEXT | string | TEXT |
| BLOB | `{"$blob":"<base64>"}` | 还原为 BLOB |

BLOB 用标记对象而不是直接丢掉：**用户改不动它，但必须能原样带回**，否则一存就把二进制字段清空。

## 3. 写入方式（四种）

| 方式 | session_id | project_id | 走哪条路 |
| --- | --- | --- | --- |
| **就地覆写**（同账号） | 保持原 id | 不变 | 删旧行 + 按编辑结果重写（照 `sync_groups_inner` 模式） |
| **新增**（同账号） | 新 24 位 hex | 不变 | 直接插入（`id` 列交给 SQLite 自增） |
| **跨账号**（同客户端内） | 新 id（同库必须换） | 改成目标账号的 project | 复用 `ensure_project_for()` + 三处 project_id 改写；**只在「新增」时可用** |
| **跨客户端** | 由目标端生成 | 由目标端决定 | 复用 `workbuddy_import::import_sessions`（WB→Trae）/ `trae_handoff::handoff_write`（Trae→WB） |

### 写入编排（逐字照 `trae_delete::delete_sessions_core` 的顺序）

1. 解析实时库密钥 `resolve_live_key()`（存盘密钥按首页 HMAC 校验，过期自动重扫进程内存）
2. **结束客户端进程** `kill_all` + `wait_until_stopped`（WAL 残留帧第 3 步合并，不丢数据）
3. 解密实时库为明文副本 `decrypt_database()`
4. **合并 WAL 已提交帧** `merge_wal_into_plain()` → `patch_reserved_field()`
5. 明文副本上改行（**单个事务**）：
   - 覆写：只删「本次改动过的表」的旧行 → 按 doc 插入（大表一行不碰）
   - 新增：直接插入（`id` 自增列不参与）
   - **`fts_*` 一律排在最后，且写之前先 `DELETE FROM t WHERE session_id = <新 id>`**（见下）
6. **增量加密回写** `write_db_incremental()`（**绝不整库重写**）
7. 整库备份（含 wal/shm）→ `prune_backups(dir, 1)` → 原子替换
8. `promote_snapshot()` 提升新明文为快照
9. 重启客户端 `launch()`

> ⚠️ 与删除不同的一点：**覆写不把会话文件移入回收站**。删除是「整条会话消失」，覆写是「改了内容」，
> 文件应保留。若会话标题变了，会话文件名可能不匹配 —— 需要同步重命名会话文件（见第 7 节）。

### 三条写入硬不变量（2026-10-10 真机实测确认）

真机探针 `examples/t46_edit_write_probe.rs` 走完整往返（新增 → 逐表比对 → 删除；覆写标题 →
验证大表未动 → 复原），把下面三条钉死：

**① `fts_*` 是触发器自动维护的虚表，必须「最后写 + 写前先清」**

| 触发器 | 时机 | 目标 |
| --- | --- | --- |
| `trg_session_title_ai` | AFTER INSERT ON `chat_session` | `fts_session_title` |
| `trg_message_content_ai` | AFTER INSERT ON `chat_message_general` | `fts_message_content` |
| `trg_session_title_au` | AFTER UPDATE OF `session_title` | `fts_session_title`（先 DELETE 再 INSERT）|
| `trg_session_physical_delete_fts` | AFTER DELETE ON `chat_session` | 清两张 `fts_*` |

我们插 `chat_session` / `chat_message_general` 时触发器**已经补了一份**词条，再照抄源库的
`fts_*` 行 ⇒ **词条翻倍**（实测 `fts_session_title` 1 行变 2 行）。但触发器补的那份**不完整**
（`trg_message_content_ai` 只取 `$.type == "text"` 的片段；源库里 `[{"text_content":…}]`
这种没有 `type` 的它取不到文本，会写出一条空词条），所以也不能干脆不写。
**正解 = 先按目标会话 DELETE（清掉触发器刚补的半成品 + 上轮残留），再整份写入**；
顺序上必须排在 `chat_message_general` 插入**之后**。既有 `copy_session` 就是这么做的。
护栏：`fts_mirror_rows_are_cleared_before_being_rewritten`。

**② 重映射只认「身份列」= UNIQUE 索引列**

主键是**自增 `id`（INTEGER，rowid 别名，`readOnly`）**，不参与重映射；真正的身份是
**UNIQUE 索引列**（`session_id` / `message_id` / `history_v2_id` / `task_id` …），
形态是 20~24 位 hex。只按「非 INT 主键」判会**漏掉 `message_id`** ⇒ 同库新增直接撞
`UNIQUE constraint failed: chat_message.message_id`（真机踩到过）。

**③ 四类列「故意不重映射」**

| 列 | 理由 |
| --- | --- |
| `project_id` / `user_id` | 账号维度，跨账号是另一套语义（S2） |
| `agent_run_id` | 指向**服务端** agent run；本机 `agent_run` 表这些会话**一行都没有**（引用本就悬空） |
| `server_task_id` | 同上，实测多为 NULL |

既有 `copy_session` 也只改 `history_v2_id` 这个唯一键、这几列原样照抄 ⇒ 保持一致。

### S2 · 跨账号写入（实现要点）

**为什么只允许「新增」**：覆写是「就地改这一条」，语义天然绑在原账号上；允许覆写顺带换账号，
等于**悄悄把一条会话从 A 账号搬到 B 账号** —— 既覆盖数据、又改变了原账号的会话清单。
风险远大于收益，所以 `edit_save` 在**碰库之前**就拒掉（`target_uid` 只在 `mode = "insert"` 时接受）。

**归属必须改三处**（T29 的坑，漏一处 = 客户端**删不掉 + 重启后记录复活**）：

| # | 落点 | 改法 |
| --- | --- | --- |
| ① | `chat_session.project_id` | `UPDATE chat_session SET project_id = ?` |
| ② | `chat_session.context` 的 `last_real_project_id` | 复用 `trae_import::rewrite_last_real_project_id()`（解析失败/无该键则保持原值，绝不写坏 context） |
| ③ | `session_project.project_id` | 由既有对齐兜底 SQL 跟着 ① 走（阶段五） |

**目标工程从哪来**：复用 `trae_import::ensure_project_for(src, dst, sid, dst_uid)` ——
在目标账号下找**同 `absolute_path`** 的未删工程，找到就复用，找不到就复制源工程行、
换新 `project_id` / `biz_project_id`、`user_id = dst_uid` 新建一条。**与既有同库复制同一条出口**，
不另写一套。

**可选账号清单**：`trae_session_edit::list_target_uids()` 读 `project.user_id`（= Trae 判定会话归属
的那一列，与 `session_owner_uid()` 同一链路），显示名统一走 `trae_vault::account_label()`。
⚠️ 前端**别自己截 uid 尾号**（T41 的教训：同一屏两个口径必然自相矛盾）。

**前端交互**：写入方式选到「新增」时才出现「写入到账号」下拉；选中非本账号时**额外弹一条独立提示**
（写清三处归属都会改、源会话不受影响）—— 这一步是改归属，不能只在 Select 里悄悄换个值。
另外「原样复制到另一个账号」是合法操作（一个字段都没改），所以写入按钮的可用条件看的是
`pendingWrite = dirty || (insert && 选了别的账号)`，而不是 `dirty`。

**真机验证**：`examples/t46_cross_account_probe.rs` —— 克隆到目标账号 → 核对
①`edit_doc.ownerUid` == 目标 uid、②`session_project.project_id` == `chat_session.project_id`、
③`context.last_real_project_id` == 同一个 project_id → 删掉克隆。

### 已知边界：JSON 载荷里嵌的服务端 id 不改

真机实测 14 个 id「原样留下」，全部住在 `chat_message_task.content` / `history_v2.messages`
这类 **JSON 载荷内部**，从来不是任何列的值 ⇒ 进不了重映射表，也就改不到。

- **这是既有语义**：`copy_session` 同样是整列照抄，`agent_run_id` 那一类也一样保留。
- **不做「按字符串暴力替换 JSON 里的 id」**：那些 id 指向的是服务端实体（agent run / 云端任务），
  本机克隆出来的新 id 反而会与源会话彻底对不上 —— 比保留更糟。
- 探针的「新旧列级 id 不相交」判据只覆盖列级，正是为了把这个已知边界显式排除在硬判据之外。

## 4. 校验：分级（硬拦 + 警告）

校验只有**一份实现**（后端纯函数 `trae_session_edit::validate()`），前端防抖调用 ——
**绝不在前端重写一遍规则**（两处独立推导必然跑偏一次，T31 的教训）。

### 硬拦（`error`，不修好不让写）

| 规则 | 说明 |
| --- | --- |
| `session_id` 格式 | 20~24 位 hex（沿用 `is_session_id`） |
| `message_id` / `turn_id` 非空 | 三张 message 表的主键不能为空 |
| 行内 `session_id` 一致 | 该会话所有行的 `session_id` 必须等于本会话 id |
| 主键不重复 | 同一表内 `session_id` / `message_id` 不得重复 |
| `message_id` 交叉引用 | `chat_message_general` / `chat_message_task` 的 `message_id` 必须都能在 `chat_message` 找到对应行（除非该表本就没有对应行） |
| 时间字符串格式 | 保持原格式字符串，**不做时区换算**（`YYYY-MM-DD HH:MM:SS` 或原样） |
| `NOT NULL` 列不得为 null | 按 `PRAGMA table_info` 的 `notnull` 判定 |
| 类型不匹配 | TEXT 列塞对象 / INTEGER 列塞中文 |
| **会话是空的**（v0.2.16 加） | doc 里 `chat_turn` 与 `chat_message` **同时为 0 行** ⇒ 客户端打开这种会话会一直卡在「环境创建中」，**发不出任何消息**（真机取证见 `docs/任务书.md` S3.5）。两张表都没进 doc 时**不判**，避免「只读元数据」误报 |

### 警告（`warning`，可继续写）

| 规则 | 说明 |
| --- | --- |
| 消息序号不连续 | `message_index` 跳号（客户端通常仍能打开） |
| 助手回答为空 | `chat_message_task` 末项不是 `finish` 或 `summary` 为空 |
| 改动了 `fts_*` | 提醒：这是检索镜像，改坏只影响搜索 |
| `context` JSON 解析失败 | 提醒客户端可能读取失败 |
| 会话标题为空 | 可用但客户端列表会显示成空白 |

前端把 `error` 显示为红色阻塞条（写入按钮禁用），`warning` 显示为黄色提醒条（可继续）。

## 5. 前端结构

### 视图范式（2026-10-10 第三次调整：入口唯一化）

第一版右栏是「**先选表、再看原始行**」：把 `chat_turn` 的全部列 + 每张关联表的行摊开成表单。
功能上没问题，但用户原话是 **「显示的太细致了，要求跟正常会话的显示一样就行，每段话独立，点击可以编辑」** ——
右栏一屏全是 `turn_id` / `reply_to_message_id` / `params.blocking`，那是数据库视角，不是会话视角。

第二版把右栏改成「会话式正文」。第三次（本轮）只动**入口**，用户原话：
**「将查看详情按钮增加为编辑会话功能，原编辑会话按钮取消；会话编辑器里面的下拉选择会话的功能取消」**。
第四次（本轮）再收一次：**页脚「关闭编辑」按钮删掉，只留右上角 ✕**。

⇒ 现在的形态：

> **页脚不再有「关闭编辑」按钮**（第四次调整，用户原话：「已经没有了选择功能，关闭编辑的按钮可以取消，
> 仅保留右上角 x 关闭就行」）。关闭动作统一由右上角 ✕ 触发（`X` → `onOpenChange(false)`），
> effect 里清临时选择，下次打开由 `loadDoc` 整份重读 ⇒ **不需要页脚再放一个同样效果的按钮**。
> 关键：✕ 与页脚按钮**走的是同一条关闭路径**，删掉页脚那个不会留下「关不掉」的分支。

**入口唯一**（本轮改动，三处一起落地）：

| 位置 | 改前 | 改后 |
| --- | --- | --- |
| 列表卡片头 | 一个独立的「编辑会话」按钮，点开**空编辑器**再在下拉里挑会话 | **删掉** |
| 列表行内 | 👁「查看详情」→ 只读详情弹窗（弹窗里再点「编辑这条会话」） | ✏️「编辑这条会话」→ **直接进编辑器**，`editSeed = 该行 id` |
| 编辑器左栏 | 会话下拉（可就地切到任意会话） | **只读**显示会话标题 + `session_id`（+ 刷新按钮），不再提供切换 |

连带的清理（「提示与入口必须同趟落地」的正面版 —— 删入口就得删指着它的东西）：

- **只读详情弹窗整块删掉**：`detail` state、`openDetail()`、`Eye` / `TraeSessionDetail` 两个 import。
  它展示的内容（元信息 + 逐回合正文）编辑器里全有，导出 MD 的能力留在列表行上。
  `api.traeSessionDetail` 与后端命令**保留**（唯一「不进编辑态、不碰库」的读取入口，排障用），
  已在 `api.ts` 注明「当前无调用方」。
- 编辑器 props：`sessions: TraeSessionInfo[]` + `initialSessionId?` → **`sessionId: string | null`**。
  ⇒ 「左栏没会话时自动选第一条」那条 effect 随之删除（不再可能出现「有列表但没选中」）。
- **⚠️ 唯一例外**：写入方式选「新增会话」写入成功后，`picked` 会跟到**新生成的 id**
  （它是 state，不是直接读 prop）—— 否则用户接着改的其实是原会话，而他以为在改刚建出来的那条。

**S5：两个「数据迁移」页的编辑入口**（本轮同趟落地）：

| 页面 | 搬什么 | 行内编辑的是 | 编辑器组件 | 关闭后 |
| --- | --- | --- | --- | --- |
| WB → Trae（`wb-import`） | WorkBuddy 会话 → Trae | **WorkBuddy** 会话 | `WorkbuddySessionEditor` | `load()` 重读候选列表 |
| Trae → WB（`wb-export`） | Trae 会话 → WorkBuddy | **Trae** 会话 | `TraeSessionEditor` | `onChanged()` 重读 |

判据：**编辑的永远是「来源那一端」**（要搬过去的那个会话）——
WB→Trae 页编辑 WB 会话，Trae→WB 页编辑 Trae 会话。
⚠️ `wb-import` 的行是 `<label>`（整行点哪儿都切换勾选）⇒ 编辑按钮必须 `preventDefault` + `stopPropagation`。

**每一段话都是独立的**：各自带自己的「编辑 / 删除」，点正文就地变成 textarea 改，
`Ctrl/⌘ + Enter` 保存、`Esc` 取消。**全字段可编辑并没有丢** ——
`chat_turn` 本体、每条消息的主行、每张关联表（含 `fts_*`）全部收进底部
「底层字段（原始表 / 全部列）」折叠块，默认收起。

### 正文是怎么拆成「一段」的（`trae-turn-model.segmentsOf`）

真机 82 条消息实测出来的结构（**不是推演**）：

| 侧 | 位置 | 实测 |
| --- | --- | --- |
| 用户提问 | `chat_message_general.content`（**数组**） | 82/82 项都是 `{type:"text", text_content}` |
| 助手回答 | `chat_message_task.content.messages[]`，每项 `{id, type:"plan_item", plan_item}` | 可读成分只有三种 ↓ |
| ↳ 说明 | `plan_item.thought` | 13 条非空 |
| ↳ 工具调用 | `plan_item.tool_call_info.name` | `finish` 24 / `Read` 17 / `RunCommand` 9 / `Edit` 5 / … |
| ↳ 答复 | `name=="finish"` 的 `params.summary` | 17 非空 / **7 空** |

⇒ 一条消息 = 若干「段」，排布顺序按 Trae 自己的时间轴：**先 `thought`（说明）再动作**（工具 / 答复）
（同一个 `messages[i]` 里 `thought` 和 `tool_call_info` 是同一时刻的「想」和「做」，
把 thought 排后面会读成「先做了再解释」）。

> ⚠️ **段的 `path` 相对 `content` 列的值**，不是相对整行。
> 用户侧是 `[i, "text_content"]`，助手侧是 `["messages", i, "plan_item", …]`。
> 写回一律 `setCell(ref, "content", setAtPath(row.content, path, value))`。
> 早先写成相对整行（带前导 `"content"`）时，`setAtPath` 会把外层的**数组整个换成对象** ——
> 单测 `setCell 把改过的 content 写回对应行的对应列` 抓到的就是这个。

> ⚠️ **删一段有三种删法，混用会连带删掉用户没打算删的东西**（`trae-session-editor.deleteSegment`）：
> `thought` ⇒ 只清空字段（它和同一条 `messages[i]` 里的工具调用是**同一个元素**）；
> `text_content` ⇒ 摘掉整个 `content[i]`；
> 工具调用 / 答复 ⇒ 摘掉整个 `messages[i]`。

> ⚠️ **新增助手段必须是 `finish` 形状**（`emptySegmentItem`）：
> `{id, type:"plan_item", plan_item:{thought:"", tool_call_info:{id, name:"finish", params:{summary:""}}}}`。
> 给空对象会变成客户端读不懂的未知类型。

> ⚠️ **大字段引用**：`chat_message_task.content` 有 **53/82 条**是按引用返回的（`$jsonRef`）。
> 按引用返回时正文**不在本地** ⇒ 卡片显示「正文是大字段，还没取回来」+ 一个「展开正文」按钮
> （走既有 `trae_session_edit_cell`），**不猜、不给空段落**。

### 全字段结构化表单：递归渲染器

因为 Trae 的表结构**随客户端版本变化**，逐个字段手写控件不可维护。做法是
**递归结构化表单** `JsonForm`：按值的实际类型渲染控件，任意深度都能展开。

| 类型 | 控件 |
| --- | --- |
| string | `<input>`；长度 > 80 或含换行 → `<textarea>` |
| number | number input，区分整数 / 小数 |
| boolean | `Switch` |
| null | 显示 `null` + 「改为 …」类型选择（string/number/bool/object/array） |
| array | 每项一行：序号 + 上移/下移/删除 + 递归控件；底部「新增一项」 |
| object | 每个键一行：键名 + 递归控件 + 「删除该键」；底部「新增键」（可选建议键名） |
| `{"$blob":…}` | 只读 + 显示 base64 长度，可切换为可编辑 base64 |

「局部修改」= 在任意深度改任意字段；「新增」= 在数组/对象里加点；「删除」= 删点。
**消息级批量删除** = 在消息列表勾选多条一次删掉。

仍需要一个**源码视图**开关（同一份 doc 的 JSON 文本），用于：粘贴整段新结构、以及递归表单改不动的场景。
两个视图共享同一份 state，切过去即所见即所得。

### 后端命令

| 命令 | 签名 | 说明 |
| --- | --- | --- |
| `trae_session_edit_doc` | `(client_key, session_id) → Value` | 读出 EditDoc（只读） |
| `trae_session_edit_validate` | `(doc) → Value` | 分级校验（只读，不碰库） |
| `trae_session_edit_save` | `(doc, mode, target) → Value` | 写入（sync 重活 → `off_main`） |
| `trae_session_edit_stats` | `() → Value` | 可写目标账号 / 客户端清单（只读） |
| `workbuddy_session_edit_doc` / `_save` | WB 侧同构 | sessions 表字段 + JSONL 逐事件 |

> ⚠️ 写库命令一律 `pub async fn` + `off_main()`，并在 `SYNC_ALLOWLIST` 之外（`main_thread_guard` 会扫）。

## 6. WorkBuddy 侧

WorkBuddy 会话**不是** SQLite 表结构：

- **元数据**：`~/.workbuddy/workbuddy.db` 的 `sessions` 表（`workbuddy_sessions::db_path()`）
- **正文**：`~/.workbuddy/projects/<工作区>/<会话id>.jsonl`，**一行一个事件**

所以编辑模型是「**sessions 表字段（结构化表单）+ JSONL 行数组（每行一个 JSON 事件，递归表单）**」。

三条硬规则（`workbuddy_sessions.rs:7-25`）必须遵守：

1. `edge-sync-mapping*.db` **一字节都不写**（`assert_not_edge_sync()`）
2. 复制 = 新 UUID + `INSERT`（**非 `INSERT OR REPLACE`**）
3. 删除走**软删**（`UPDATE sessions SET deleted_at …`）+ 正文进回收站

### S4 实现要点（2026-10-10 落地）

后端 `modules/workbuddy_session_edit.rs`（约 1500 行，20 条单测）：

| 命令 | 签名 | 说明 |
| --- | --- | --- |
| `workbuddy_session_edit_doc` | `(uid, cid) → Value` | 只读；返回 `{row, columns, body{path,workspace,exists,bytes,lineCount}, turns, head, counts, lineKinds, warnings}` |
| `workbuddy_session_edit_lines` | `(uid, cid, from, to) → Value` | 按行区间取完整行，**上限 400 行/次** |
| `workbuddy_session_edit_targets` | `() → Value` | `sessions.user_id` 去重 + `label_for` |
| `workbuddy_session_edit_validate` | `(ops, row_patch, columns, summary, session_id) → Value` | 前端快速校验，**不读文件、不开库** |
| `workbuddy_session_edit_save` | `(uid, cid, mode, ops, row_patch, target_uid) → Value` | 写入（`off_main`） |

**① 读分两步，写只回传 ops —— 因为正文体积是硬约束。**

真机单会话正文 **19 MB**，最大单行 **136 MB**。整份 doc 过 IPC 会把前端冻死，
所以读先给「回合索引 + 每行轻量预览」（`LineInfo`：`kind` / `textPath` / `preview`），
要完整行再按区间取（`edit_lines`）。**写入走 ops 操作数组**：

```
OutLine::Orig(usize)  ← 未改动的行，按原索引**逐字节原样带回**
OutLine::New(String)  ← 只有改动 / 新增的行才重新序列化
```

`apply_ops` 支持 `replace` / `delete{indexes}` / `insert{at}` / `append`；
同行既改又删、越界索引、非对象 payload 一律报错（单测 `same_line_cannot_be_both_replaced_and_deleted` /
`out_of_range_index_is_rejected` / `non_object_payload_is_rejected` 钉住）。
⇒ 用户只改一段 text，其余 3183 行的字节**一个都没变**（单测 `untouched_lines_stay_byte_identical`）。

**② 两层校验。**

- 前端 `validate_submit`（`workbuddy_session_edit_validate`）：**不读文件、不开库**，
  靠 `doc.counts` / `doc.lineKinds` 算 `after = before − 删掉的用户提问 + 新增的用户提问`，
  **`after == 0` 直接硬拦**（对应 Trae 侧「chat_turn / chat_message 同时为 0」）；
  外加元数据列校验（主键不可改、NOT NULL 不可空、INTEGER 列类型）。
- 写入前 `validate_full`（后端私有，解析整份结果）：空行 / 非法 JSON / 重复 id 报 **error**；
  `parentId` 断链、`callId` 孤儿只 **warning**。
  **全量错误以 `ok=false` 正常返回**（不是 `Err`），前端照样能显示逐条错误。

**③ 行结构校验 `check_line`**：`type` 非空、`id` 是 UUID、`message.role ∈ {user, assistant}`、
`content` 是数组、`function_call` 要有 `name`/`callId`、`function_call_result` 要有 `callId`、
**`sessionId` 必须等于本会话**（单测 `validate_submit_rejects_wrong_session_id_in_new_line`）。
未知 `type` 只记 warning，不拦（客户端版本会加新事件类型）。

**④ 用户提问的识别复用 `workbuddy_source::extract_user_text`**（同一套规则，不另写一份）；
`auto` / `summary` 行**不开新回合**（单测 `classifies_real_user_question_but_not_summary`）。
真实用户提问的正文形如 `[system-reminder 块…][<user_query>真实提问</user_query>]`，
前端 `replaceUserQuery` **只换 `<user_query>` 内层**，护住前面的 reminder 与后面的附加块。

**⑤ ⚠️ 快照陷阱：`-shm` 不复制，且 `fs::copy` 会失败。**

WorkBuddy 客户端正把 `workbuddy.db-shm` 内存映射着，而 `std::fs::copy` 走 `CopyFileExW`
只申请 `FILE_SHARE_READ` ⇒ **`os error 1224`**（「请求的操作无法在使用用户映射区域打开的文件上执行」）。
`workbuddy_source::list_sessions` 全走 `snapshot_db()` ⇒ 表现为**「WorkBuddy 在跑时会话记录页整个打不开」**。
正解：`copy_shared()` 手工 `File::open` + `io::copy`；**`-shm` 不复制**（让 SQLite 自己从 WAL 重建）；
且先清上一轮快照残留（`-wal` 残留会让新快照读到**上一次**的事务帧），末尾打开一次让索引重建。

**⑥ 复用而非另写**：`open_rw` / `row_owner` / `read_source_row` / `target_columns` /
`insert_copy_row` / `backup_db` / `target_body_path` 全部从 `workbuddy_sessions` 放宽为 `pub(crate)`。

**⑦ `edit_save` 的 `target_uid` 只在 `mode=="insert"` 可用**（与 Trae 侧同款约束：覆写只能写回原账号）；
`insert` 时正文里 `replace_session_id` 换新 id，且校验目标账号存在。
占用门禁：`workbuddy_switch::is_running() && current_uid == dest_uid` ⇒ `TARGET_IN_USE`。

**⑧ 写流程**：备份库 + 备份正文 → 写正文（`.tmp` 再 rename 的 `atomic_write`）→
写行（覆写 `update_row`；新增读源行合 patch 后 `insert_copy_row`）→ 写后校验（归属 + 行数回读）。

### 前端形态（`workbuddy-session-editor.tsx`）

与 Trae 侧同构：左栏「会话开头 + 回合列表」，右栏「会话式正文」（一段一条，点即改）。
差异只在**段落的来源**：Trae 是 `content` 列里的 JSON 载荷，WorkBuddy 是 **JSONL 的 n 行**。

- 行 `kind`：`user` / `auto` / `summary` / `assistant` / `reasoning` / `tool_call` / `tool_result` / `meta` / `message` / `unknown`
- 默认收起 `tool_call` / `tool_result` / `meta` / `message`（用户要的是「跟正常会话一样」）
- 底层字段折叠块用 `RowForm` 画 `sessions` 全字段（`rowDraft` → `rowPatch` diff）
- 页脚：写入方式 Select / 写入到账号 Select（仅 insert）/ `撤销改动` / `就地改写|新增写入`
- **⚠️ 编辑器页脚没有「关闭编辑」按钮** —— 关闭只认右上角 ✕（见 §5 收敛说明）
- 搜索框下一行是**多选工具条**：`多选删除`（开关）/ `已选 N / M` / `全选`（只作用于当前搜索结果的可见回合）/ `清空` / `删除选中（N）`。
  多选态下**点整行 = 切换勾选**（同时把右栏切过去，边勾边看）；逐个 🗑 在多选态下照样可用，两者不互斥。
  勾选指示画在回合按钮**内部**（纯展示 `span`，`data-turn-check` 便于自查），不引入嵌套按钮。

#### 回合级删除（第五次调整）

左栏每个回合行末尾一个 🗑（兄弟节点，不是嵌在回合 `<button>` 里 —— 嵌套 `<button>` 非法），
右栏头部另给一个「删除本回合」。两条路都走同一个 `askDeleteTurns(indexes)`：

- 常规：确认框写明「会移除该回合名下的 N 行（第 a–b 行）」，确认后 `removeTurns(indexes)`
  —— 区间内每行进 `edit.deleted`，区间内的本次新增行一并剔除，并清掉同行残留的 `replaced`。
- **删到最后一条用户提问** ⇒ 不提供「删到空」，改道成「彻底删除整条会话」（见 §9 护栏 20）。
- 删完不是立刻动库：写入前「撤销改动」可全部收回（`undoAll` 也会清 `removedTurns` / `multiSel`）。

#### 批量删除回合（第六次调整）

用户原话：**「workbuddy 的回合删除按钮需要鼠标放上去才显示，要求跟 trae 一样，一直显示 / 新增批量删除回合的功能，多选删除」**。

- 单个接口统一成 `askDeleteTurns(indexes: number[])`：单回合就是 `[index]`（右栏按钮与行内 🗑 都传单元素数组），
  多选传整批 —— 空会话硬拦因此**天然按整批算**（护栏 22）。
- 确认框按 1 个 / N 个分文案：单回合仍列「第 a–b 行」，多回合列「这 N 个回合名下的 M 行」+ 回合序号清单。
- 删完 `multiSel` 里被删的下标要清掉，否则「删除选中」会带着幽灵下标（护栏 22 的注释同款理由）。

#### 导入会话的回合识别 + 账号分离 + 确认框换行（第七次调整 · v0.2.22）

用户原话三条：**「从 trae 导入到 workbuddy 的会话，会话回合无法正常识别」/
「workbuddy 导入 trae。trae 不应该多选账号，trae 和 trae solo 应当分离」/
「会话回合删除的时候，当内容过长，会超出显示，应当设置自适应换行」**。

**① 回合识别**：Trae → WorkBuddy 导出的用户行只有裸文本（没有 `<user_query>` 壳），
而 `classify_line` 当时按「有没有壳」二分 ⇒ 这类会话 **0 个回合**（左栏「这条会话没有任何回合」）。
读端改走 `classify_user_message` 单一出口（旧会话免重导即可识别，护栏 23），
写端 `push_user` 补壳 + `startsNewUserRequest`（护栏 24）。
左栏告警随之变精确：真·0 提问才报「没有一条用户提问」；**有提问但没壳**给 milder 提示。

**② 账号分离**：`CrossWriteAccount` 增加 `clientLabel`，新增 `crossKeyOf()` 复合键（护栏 25），
页脚拆「写入到客户端」pill + 该客户端的账号下拉（护栏 26）；
`pickCrossClient(key)` 落到该客户端第一个账号，只有一个客户端时不渲染 pill 行。

**③ 确认框换行**：`min-w-0` + `break-all whitespace-pre-wrap`（护栏 27，Trae 侧同款弹窗一并改）。

#### Trae 侧批量删回合（第八次调整 · v0.2.23）

用户原话：**「Trae 侧要做批量删回合」**。第六次调整只做了 WorkBuddy 侧，Trae 侧仍是逐个 🗑 —— 两边能力不对齐。

**做法：不新写一套，把 Trae 的单回合删除也改道走批量那条路。**

```ts
const askDeleteTurn = (turn: TurnView) => askDeleteTurns([turn.key]);
```

这样「一个回合名下有哪些行」只有 `turnRefs` → `deleteRowRefs` 一份推导（护栏 29）。
两处各写一遍的话必然在某次调整里跑偏一次，而症状是「删完客户端里还留着一半」。

两点与 WorkBuddy 侧**故意不同**，别互相抄（护栏 28）：

| | WorkBuddy | Trae |
| --- | --- | --- |
| 勾选键 | **原始行号**（删完不重排 ⇒ 下标稳定） | **`TurnView.key`（`turn_id`）**（删行会让行号整体前移） |
| 空会话计数 | 数「还剩几条用户提问」（`usersAfterTurnsRemoved`） | 数「还剩几个回合」（`turnsLeftAfterRemoving`） |

UI 与 WB 侧逐块同构：搜索框下一行工具条（`多选删除` / `已选 N / M` / `全选` / `清空` / `删除选中（N）`），
多选态下**点整行 = 切换勾选**并顺带把右栏切过去；勾选指示是回合按钮**内部**的纯展示
`span[data-turn-check]`（嵌套 button 非法）；🗑 保持常显、仍是回合按钮的兄弟节点。

新增 effect 摘掉已消失的勾选键（与 `selMsg` 那条对称），否则「已选 N」会挂着删不动的幽灵。

## 7. 会话文件与标题

Trae / WorkBuddy 都有「会话文件」目录（`trae_delete::collect_session_files()`）。覆写改了标题后：

- 文件名若含标题 → 需要同步重命名，否则客户端按标题找不到正文
- 本轮策略：**按会话 id 定位文件（而非标题）**，标题变化时**同步重命名**；
  重命名失败只记 warning，不回滚库写入（库是权威，文件按 id 兜底）

> 真机实测：`collect_session_files()` 是按 **session id** 定位目录（`snapshot_root(client).join(sid)`），
> 所以覆写改标题**不会造成「找不到正文」**；重命名只是让目录显示名跟上。
> 检索标题 `fts_session_title` 由触发器自动跟新标题，**不需要我们手写**（见 §3 不变量①）——
> 覆写只标了 `chat_session` 一张表时，检索标题也已经变成新的了（真机确认）。

## 9. 护栏（必须带）

1. **写库命令必须 `off_main`**，登记进 `commands.rs` 的既有检查（`heavy_commands_must_not_be_sync`）。
2. **绝不整库重写**，只用 `write_db_incremental`；回归测试已存在，别绕过。
3. **写前必须合并 WAL**；护栏 `every_wal_removal_site_merges_wal_first` 会扫源码。
4. **校验只有一份实现**（后端纯函数），前端只显示不重算。
5. **覆写前整份备份**，界面提供「撤销到编辑前」（复用备份目录，不需要新机制）。
6. **BLOB 必须可逆往返**（`$blob` 标记），单测钉住。
7. **错误与空必须长得不一样**：读失败返回 `Err`，前端撤掉空态卡并写明「这是读取失败，不是数据被删」。
8. 幂等：连续两次写入同一份未改动的 doc，第二次应报告「无变化」而不是重复写库。
9. **段的 `path` 相对 `content` 列的值**（不是相对整行）。写成相对整行时 `setAtPath` 会把外层
   **数组整个换成对象** —— 已由单测 `setCell 把改过的 content 写回对应行的对应列` 钉住。
10. **删一段的三种删法不许混用**：`thought` 只清空字段（它和同一条 `messages[i]` 里的工具调用
    是**同一个元素**）；`text_content` 摘 `content[i]`；工具调用 / 答复摘 `messages[i]`。
11. **新增助手段必须是 `finish` 形状**（`emptySegmentItem`）；给空对象会被客户端当成未知类型。
12. **大字段引用不许猜**：`content` 是 `$jsonRef` 时只给「展开正文」按钮（走 `trae_session_edit_cell`），
    不给空段落、不按 preview 推内容。
13. **渲染自查的判据必须唯一且指向「展开后才出现」的东西**：折叠块的**副标题在收起时也渲染**，
    用文案判会误报「已展开」；图标按钮一律给 `aria-label`，否则 `json-form` 里同名按钮会被一起数进来。
14. **入口唯一**：编辑器只能从列表行内的「编辑这条会话」进（`editSeed` = 该行 `id`）。
    卡片头那个独立入口、只读「会话详情」弹窗、左栏会话下拉**都不许复活** ——
    判据：全仓 `setEditOpen(true)` 只有 **1 处**；编辑器 props 里不许再出现 `sessions` / `initialSessionId`。
    反面同样算：**要在编辑器里加一个「切到别的会话」的动作，就必须先回答「那列表行的点击算什么」**。
15. **关闭只有一个出口**：编辑器页脚**不许再放「关闭编辑」按钮**（第四次调整）。
    删的时候要确认它与右上角 ✕ 走的是**同一条** `onOpenChange(false)` 路径 ——
    否则会出现「按钮删了、✕ 那条路却没清临时选择」的幽灵。
16. **未改动的行必须逐字节原样保留**（`OutLine::Orig`）。护栏：单测 `untouched_lines_stay_byte_identical`。
    别用「整份重新序列化」替代 —— JSONL 的键顺序 / 空白 / 浮点写法都会变，客户端可能读不回来。
17. **`-shm` 不许进快照**，且复制必须用 `File::open` + `io::copy`（`copy_shared`），**不能用 `fs::copy`**。
    判据：WorkBuddy 在跑时快照要能成功（否则 `list_sessions` 全线 `os error 1224`）。
18. **编辑入口落在 `<label>` 行内时必须 `preventDefault` + `stopPropagation`**：
    「数据迁移」页（`wb-import`）整行是勾选用的 `<label>`，点哪儿都会切换勾选；
    编辑按钮在行内 ⇒ 不拦就变成「点编辑顺带勾/取消勾了这条」。
19. **两套数据模型不许共用一段拆分逻辑**：Trae 的「段」来自 `content` 列的 JSON 载荷
    （`segmentsOf`），WorkBuddy 的「段」来自 **JSONL 的 n 行**（`classify_line`）。
    共用会把「一行」和「一段」混为一谈 —— 前者可增删行，后者只能在既有结构里挖点。
20. **删回合 = 把该回合区间的行全量标删，行号一律用原始行号，不许重排**（第五次调整）。
    - 判据：删除后其余回合的 `start/end` 一个数都不变；`ops` 里只有 `delete{indexes}`。
    - **落在这个区间里的本次新增行必须一起带走**（`at ∈ (start, end]`），
      否则它会像幽灵一样挂到下一个回合的开头。
      ⚠️ 左端是**开区间**：`at === start` 是「插在回合第一行之前」，属于「会话开头」那一档。`usersAfterTurnRemoved` 的剔除区间必须与之**逐字一致**，否则前端计数与后端硬拦会漂。
    - **计数口径必须与后端 `validate_submit` 同源**：`usersAfterEdit` / `usersAfterTurnRemoved`
      （`lib/wb-turn-model.ts`）就是「改完后还剩几条用户提问」，两边算出来必须一致。
    - **删到一条用户提问都不剩 ⇒ 不给删，改道成「彻底删除整条会话」**
      （`api.workbuddySessionDelete`），与 Trae 侧 `askDeleteWholeSession` 同一套理由：
      空壳会话让客户端永远卡在「环境创建中」。
21. **破坏性按钮不许「hover 才显形」**（第六次调整）：左栏回合行的 🗑 必须**常显**，
    与 Trae 侧一致。hover 才出现的按钮在触屏 / 键盘 / headless 下等于不存在。
    判据：无 hover 时 `getComputedStyle(btn).opacity === "1"`（旧实现是 `opacity-0 group-hover:opacity-100`）。
22. **批量删除回合必须按「一次要删的全部回合」算空会话**，不许逐个调用单回合版本（第六次调整）。
    - 反面教材：逐个算 `usersAfterTurnRemoved` 都 ≥1、合起来删完归 0 —— 直接写出空壳会话。
    - 正解：`usersAfterTurnsRemoved(kinds, edit, turns[])`，单回合版本是它的退化情形
      （`return usersAfterTurnsRemoved(kinds, e, [turn])`），两个函数**必须同解**。
    - 同理，`removeTurns(indexes)` **不是**循环调用 `removeTurns([i])`：一次算完所有区间再落 state，
      否则中途的 `removedTurns` 闭包会把后面的判断带偏。
23. **「是不是用户提问」只许有一个出口**：判据一律走 `workbuddy_source::classify_user_message`。
    `workbuddy_session_edit::classify_line` 与 `classify_json_kind`（`validate_submit` 里数新增提问用）
    **都必须调它** —— 两处各写一份「有没有 `<user_query>` 壳」的二分，会让「编辑一条没壳的老提问」
    被算成「删掉 1 条、新增 0 条」，单回合的导入会话一改就被误判成空会话而拒写。
    判据：原生会话里「没壳的 `role=user`」必须是 auto/summary（实测 4 条会话 43/415/36/7 行逐条 `real == wrapped`），
    而 Trae → WorkBuddy 导出的裸提问必须能开出回合。
24. **导出写出的用户行必须带 `<user_query>…</user_query>` 壳**（+ `providerData.startsNewUserRequest: true`）。
    写的一端不对齐，读的一端再宽容也只是「本工具能用、客户端不认」——
    空壳/裸提问正是「客户端打开可能显示空白」的温床。判据：单测
    `exported_lines_are_recognized_by_the_session_editor`（导出 → `classify_line` → `build_turn_index` 全链）。
25. **跨端写入目标只能是复合键 `clientKey::uid`**（`crossKeyOf()`）：Trae CN（IDE 版）与 TRAE SOLO CN
    是两个客户端，**同一个 uid 在两个客户端下各有一份**（真机 3 个 uid 全是两套）。
    只按 `uid` `find()` 会命中列表里靠前的那个 ⇒ **选了 SOLO 实际写到 IDE 库**。
    组件状态、`SelectItem value`、`defaultKey`、查表**一律用复合键**，别留 `uid` 单键的尾巴。
26. **Trae 与 TRAE SOLO CN 在页脚必须分开选**：先「写入到客户端」（pill 行，**只有 >1 个客户端时才渲染**）
    再「写入到 <对面> 账号」（下拉只列当前客户端的账号）。
    判据：切到另一个客户端后，下拉 `[role=option]` 的条数 = 该客户端的账号数（自查里 2 → 1）。
27. **Radix `AlertDialogContent` 是 grid + auto 列**：子元素默认 `min-width: auto`，
    内容里只要有一行 `nowrap`（`truncate`）的长文本，**整个弹窗会被撑到卡片外**。
    护法：弹窗加 `max-w-[min(44rem,calc(100vw-2rem))]`、`AlertDialogHeader` 与 body 加 `min-w-0`，
    长文本一律 `break-all whitespace-pre-wrap` 自适应换行。
    判据：`alertOverflow.worstOverflow`（卡片内任一元素右边界超出 `[role=alertdialog]` 的最大像素）；
    反证：旧写法 **536** → 新写法 **0**。
28. **批量删回合的「勾选键」两端不同，别互相抄**（第八次调整）：WorkBuddy 用**原始行号**
    （那边删完不重排，下标稳定）；**Trae 必须用 `TurnView.key`（`turn_id`）** —— 那边删行会让
    行号整体前移，用下标当勾选键，删掉一个回合之后其余勾选会悄悄指向别的回合。
    同理空会话计数两端也不同：WB 数「还剩几条用户提问」，Trae 数「还剩几个回合」。
29. **单个删除与批量删除只许有一条路**（第八次调整）：Trae 侧 `askDeleteTurn(t)` =
    `askDeleteTurns([t.key])`；空会话判定抽成纯函数
    `trae-turn-model::turnsLeftAfterRemoving(turns, keys)`，与「`left === 0` ⇒ 改道删整条会话」同源。
    判据：单测「逐个问都 ≥1、合起来归 0」必须能挡住「逐个算」的写法
    （反证：把该函数临时改回逐个算 ⇒ 两个用例当场失败，还原后 78 全绿）。
