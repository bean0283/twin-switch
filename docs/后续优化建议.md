# TwinSwitch 后续优化建议

> 盘点时间：2026-10-06　当前版本：**v0.2.0**
> 依据：实际读源码 + 实测命令，非照抄旧记录。旧记录中已过时的结论已在文中标出。

---

## 一、建议优先做（投入小、收益明确）

### 1. `npm test` 目前是死的 ⭐ 最该修

**实测**：

```
$ npx vitest run
No test files found, exiting with code 1
include: src/**/*.test.ts
```

`package.json` 里有 `"test": "vitest run"`，`vitest@^5.0.2` 装了，`vitest.config.ts` 也在，
但 **`src/` 下一个 `*.test.ts` 都没有**。这条命令**必然失败**。

**两种收尾方式，选一种**：补上测试文件，或删掉这条脚本。
留一个必然失败的命令在那儿，比没有更糟——它会让「跑过测试了」这件事失去意义。

**最该先补的三个**（都是纯函数，不用起 Tauri，写起来快）：

| 文件 | 为什么它最危险 |
| --- | --- |
| `src/lib/credit-package-names.ts` | `PackageCode` → 显示名的映射 + 回落链。30 多个包全叫「CodeBuddy个人版国内运营裂变包」，映射错了**不报错，只是显示错的积分来源** |
| `src/lib/storage-keys.ts` | 新旧键兜底（新键优先 → 旧键 `trae-switch-cn` → 写回新键）。错了会**静默丢用户配置** |
| `src/lib/avatar-tone.ts` | 纯色值计算，纯函数，最好写 |

> 这三个都是「**错了不崩，只是悄悄不对**」的类型。这类 bug 最贵，因为它们不会被任何现有机制发现。

---

### 2. 代理配置要手写 JSON，且没有任何界面入口 ⭐

**现状**：`~/.twin-switch/update.json` 的 `proxy` 字段，是 GitHub 连不通时唯一的自救手段。

**但**：

- 全项目搜 `update_config` —— **只有 Rust 侧读取，前端零调用**
- `src/pages/` 下 9 个页面，**没有一个是设置页**
- 侧栏 8 个导航项，**没有任何设置入口**

**⇒ 普通用户遇到「检查更新一直转圈」时，完全无从下手。**
如果这个软件要给别人用，这是最容易劝退的一类问题——用户不会想到要去手写一个 JSON。

**建议**：在更新对话框里加一个「网络设置」折叠项（一个输入框 + 保存按钮），
并且在**检查失败且错误像网络问题时，直接把入口指过去**（这一步比输入框本身更重要）。

---

### 3. 没有「跳过此版本」

`update-entry.tsx` 里搜不到任何 `skip` / 忽略逻辑。

当前行为是「有新版本就一直提示」。用户如果因为某个原因不想升当前这版（比如在等某个修复），
只能被反复打扰，没有「我知道了，别再提这版」的选项。

**代价很小**：`localStorage` 存一个 `skippedVersion`，与 `latest` 比对时跳过。
⚠️ **注意不要因此漏掉更高的版本**——只在版本号**恰好等于**跳过值时静默，出现更高版本照常提示。

## 二、自动更新的纵深加固（有安全价值，但要权衡）

### 4. `requireSignedVersion` 未开 —— 真实缺口，但现在开了会全断

**已实测**：`TwinSwitch_0.2.0_x64-setup.exe.sig` 解码后，trusted comment 是

```
timestamp:1791275978	file:TwinSwitch_0.2.0_x64-setup.exe
```

**只有 `timestamp` 和 `file`，没有 `version:` 字段**（本地 `@tauri-apps/cli` = 2.11.4）。
插件是靠 `version:` 前缀去比对版本的，找不到直接报 `MissingSignedVersion`。
**⇒ 现在开这个开关，更新通道立刻全断。**

**风险是什么**（插件源码注释原文的意思）：`latest.json` **清单本身不签名**，
签名只覆盖下载下来的那个包。所以能伪造清单响应的人，可以把**版本号写大**、
同时配上**旧版本的 `url` 和 `signature`**，让客户端"升级"到一个真实签名但已过时的包。

**暴露面客观评估**：攻击者需要能伪造 `github.com` 的 HTTPS 响应（受信证书 MITM，
或 DNS + CA 同时沦陷）。**门槛不低，所以不急。**

**要做就是一条链**：升 CLI → 确认签名里带上了 `version:` → 下一个补丁版本开启 → 重签重发。

---

### 5. CSP 未配置

`tauri.conf.json` 的 `app.security.csp` 是**空的**。

这个应用会**读解密后的账号库，并把里面的文本渲染到界面上**（会话标题、项目路径等）。
多一道 CSP，能在万一出现 DOM 注入时把外连通道掐掉。**低成本的纵深防御。**

## 三、旧记录核实结果（有几条是过时账）

我之前基于上下文给过一份建议，这次实际核对后发现**有几条已经过时了**，一并更正：

| 旧结论 | 核实结果 |
| --- | --- |
| P0-1「切换是否重写 `storage.json`」 | **已闭环，是过时账**。`trae_carriers.rs` 已实现「载体」概念（storage.json + 深度≤5 的 leveldb，上限 16 条），注释明写「只换 storage.json 会出现半新半旧的登录态」 |
| P0-2「重复会话合并」 | **仍未实现**。但我认为**这未必该做** —— 见下 |
| P2-6「没有任何测试」 | **已大幅改善**：`#[test]` 现有 **185 个**（旧记录写的「133 passed」已过时） |
| P2-7「绝对路径残留」 | **已清理**，全项目搜不到 `D:\htw` 硬编码 ✅ |
| P2-8「`types.ts` 命名残留」 | **仍在，但属误报**。`"workbuddy"` 是产品线的**真实标识**，不是旧名的残留，**不要改** |

### 关于「重复会话合并」—— 我建议不做

两条重复会话分别归属源账号与导入目标账号，**内容都是真实的**。

强行合并等于**伪造数据**：把两份真实存在的会话记录抹掉一份，还会让「换个账号登录能看到什么」
这件事变得不可解释。跨账号导入本来就该留两份。

**建议改成**：不合并，但在导入结果里**明确标注来源账号**。
比合并更诚实，也更省事。

## 四、还没解决的两条（需要真实账号验证）

这两条**动手前要先确认是否仍成立**，我不能靠旧记录下结论：

1. **统一密钥获取策略** —— 让 `trae_import` 与 `trae_delete` 走同一条
   「存盘 → 校验 → 过期重扫」链路。旧的 P1 说两条链路策略不一致。
2. **跨账号导入长周期验证** —— 需要拿真实账号跑一段时间，确认云端双向同步
   会不会回滚本地新增的孤儿行。`trae_import.rs` 的注释里明写了这个担忧。

## 五、我的排序建议

如果要动手，**按这个顺序**：

1. **修 `npm test`**（半天）—— 一个必然失败的脚本会污染整个「测试通过」的可信度
2. **补 `credit-package-names.ts` 等三个纯函数测试**（半天）—— 投入最小、防的是最贵的静默 bug
3. **更新对话框加代理入口**（一天）—— 直接决定别人能不能自己解决网络问题
4. **「跳过此版本」**（半天）—— 体验小改进，改动面很小
5. **CSP**（半天）—— 纵深防御，验证一下界面渲染没被拦即可
6. **`requireSignedVersion`**（要连升 CLI + 重签重发）—— 不急，等下一个正式版本一起做

**另外**：v0.1.0 的安装包没有更新能力，**必须先手动装一次 v0.2.0**，
之后才能自动收到后续版本。这件事记得跟使用者交代。
