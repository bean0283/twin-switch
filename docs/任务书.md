## 1. 项目概况

| 项 | 内容 |
| --- | --- |
| 名称 | **TwinSwitch · 双栖**（v0.0.24 起；原名 trae-switch-cn。Tauri 2 + React 19 + TypeScript + Rust） |
| 工作目录 | `D:\htw\签到\trae-switch-cn` |
| 核心库 | `crates/wb-switch-core`（不依赖 Tauri，可被 CLI/测试复用） |
| 桌面壳 | `src-tauri`（`commands.rs` 命令层 + `lib.rs` 注册表） |
| 前端 | `src/`（`pages/` 页面、`components/` 组件、`lib/api.ts` 调用封装、`lib/trae-types.ts` 类型） |
| 工作数据 | `~/.twin-switch/`（解密快照、备份、回收站都在这里） |
| 目标数据 A | Trae 客户端数据（SQLCipher 4 加密库） |
| 目标数据 B | WorkBuddy 数据（`~/.workbuddy/`，明文 JSONL + SQLite） |

### 1.1 两条迁移链路

```
WorkBuddy  ──(导出 JSONL + 插 sessions 行)──►  Trae 加密库      入口 /workbuddy-import
Trae 加密库 ──(读快照 + 转换)──────────────►  WorkBuddy 明文库   入口 /workbuddy-export
WorkBuddy 本机残留 ──(扫描 + 受控清除)─────►  回收站 / 彻底删除    入口 /workbuddy-cleanup
```

### 1.2 关键路径与常量

| 用途 | 位置 |
| --- | --- |
| 工具工作目录 | `~/.twin-switch/`（`config::store_dir()`） |

### T1 · 账号显示名（谁是谁）

| 字段 | 内容 |
| --- | --- |
| **状态** | ✅ 已实现，待真机确认显示效果 |
| **问题** | 界面上一律显示 `uid …97eac1`，多账号（本机 3 个）时完全分不清谁是谁 |
| **调研结论** | WorkBuddy **没有**本地账号表。可用的三个来源（可信度由低到高）：①`logs/*.log` 里的遥测行 `"userId":"…","username":"…","userNickname":"…"`（覆盖最全，但会被日志轮转清掉）；②`~/.wb-switch/accounts.json`（含手机号，装了才有）；③`storage/skeleton/account-snapshot.json`（WorkBuddy 自己写的，**只覆盖当前登录账号**） |
| **本机实测结果** | `…97eac1`→`13780001455`（当前登录，免费版）· `…be81ba`→`弦ྂ思ྂ`（手机 18858464309）· `…5d5e70`→`19550125362` |
| **设计** | 新增 `workbuddy_accounts.rs`：三来源按可信度依次合并（非空字段覆盖）、`label()` = `昵称（uid …尾6）`、`meta()` = `手机号 · 个人版 · 免费版`（自动去掉与显示名重复的部分）；**只读 uid/昵称/手机号/邮箱/类型/版本，绝不读 token**；`{nickname:{$wbEncrypted:…}}` 这类加密信封对象一律忽略（否则会把对象当字符串透传导致前端白屏） |
| **改动文件** | 新增 `crates/wb-switch-core/src/modules/workbuddy_accounts.rs`；`workbuddy_export.rs`（`target_info` 输出 `name/meta/kind/edition/name_source`，`target_label` 改用 `label_for()`）；`workbuddy_import.rs`（`list_source_sessions` 增加 `accounts` 数组）；`workbuddy-import-card.tsx`（按 uid 查表显示）；`WorkbuddyExportPage.tsx`（主行给名字、副行给 uid 尾号+版本+会话数） |

### T3 · 本机清理（扫描 + 受控清除）

| 字段 | 内容 |
| --- | --- |
| **状态** | ✅ 已实现，**未在本机执行过清除**（见下方「为什么没代跑」） |

| **安全约束（逐条对应实现）** | ①`scan()` 只用只读连接 + 遍历，绝不写；②清除前先退出 WorkBuddy（否则改库会被客户端内存快照覆盖）；③改库前整份备份 `workbuddy.db` 与 `edge-sync-mapping-v*.db`（含 WAL/SHM）；④文件默认**移入工具回收站**保持相对路径、可搬回，只有勾「彻底删除」才 unlink；⑤同步映射表一起清；⑥确认弹窗逐条列出将被处理的路径，彻底删除前用**加粗红字**警告不可逆 |
| **本机实测（只读扫描）** | 39 项 / **542.4 MB**，其中推荐清理 24 项 / 185.9 MB；大头：`logs/sandbox` 210.7 MB、`logs/2026-09-27` 80.7 MB；占用实测 `workspace` 2.74 GB（当前会话在用，**勿清**）、`binaries` 483 MB、`logs` 478 MB、`plugins` 128 MB、`traces` 88 MB |
| **改动文件** | 新增 `crates/wb-switch-core/src/modules/workbuddy_cleanup.rs`；`workbuddy_export.rs`（`wb_kill_all`/`wb_wait_stopped`/`wb_launch`/`open_wb_db_ro` 提升为 `pub(crate)` 复用）；`commands.rs` + `lib.rs`（`trae_wb_cleanup_scan` / `_purge` / `_empty_trash`）；`api.ts` + `trae-types.ts`；新增 `src/pages/WorkbuddyCleanupPage.tsx`；`App.tsx`（侧栏新增「本机维护」区 + 路由 `/workbuddy-cleanup`） |

| **验收** | `cargo test -p wb-switch-core`（含 `purge_db_rows_skips_missing_table`、`copy_dir_copies_recursively`）；`wb_audit` 第 3 节；真机：在 TwinSwitch 里点「WorkBuddy 清理」→ 扫描 → 勾推荐项 → 清理到回收站 → 打开 WorkBuddy 确认列表变干净 |

### T5 · 修复「详细过程在 Trae 里显示异常」（v0.0.11）

| 字段 | 内容 |
| --- | --- |
| **用户反馈** | 导出到 Trae 的会话，WorkBuddy 里看到的工具调用 / 思考过程，在 Trae 里显示奇怪（工具卡片不见、参数不成形） |

### T16 · 启动缓存：先读缓存 → 后台刷新 → 写回缓存（v0.0.17）

> 对应用户需求：「启动较慢，首页要加载很多信息，加载期间无法操作。你设置一个缓存，启动先读缓存，然后后台自动更新信息，更新后的信息实时写入缓存，方便后期加速启动」。

| 字段 | 内容 |
| --- | --- |
| **根因** | 首页原来在**组件挂载时** `await app_overview_snapshot()`。这个调用要枚举进程（WMI，几百 ms～数秒）+ 统计 SQLite + 递归数会话正文；期间整页骨架屏，**点不了任何东西**。而且数据只活在内存里，进程退出就没了 —— 每次冷启动都要重跑一遍 |
| **缓存落点** | `~/.twin-switch/cache/`（**新增** `config::cache_dir()`）。刻意与 `store_dir()` 分开：`store_dir` 存用户资产（账号库 / 回收站 / 解密快照），`cache` 只存**可再生的派生数据**（总览、积分），删掉只是变慢不会出错 |
| **通用读写助手** | `config::write_cache_json(name, &value)` / `read_cache_json(name) -> Option<Value>`（自动建目录；写走 `atomic_write`；失败只 `eprintln` 不影响主流程） |
| **总览缓存** | `cache/overview.json` = `{version, generatedAt, snapshot, reclaim}`。`CACHE_VERSION` 一改即视旧缓存为不存在，避免前端读到半新半旧的对象 |
| **三个新入口** | ① `app_overview::cached()` —— **只读文件不重算**，返回 `{ok, empty, generatedAt, ageMs, snapshot, reclaim}`；② `snapshot()` —— 算完**立刻写回**（保留上一份 `reclaim`）；③ `app_overview::save_reclaim(trae, wb)` —— 把前端并行扫出的可回收空间并进缓存 |
| **积分缓存** | `cache/credits.json` = `{version, at, items, errors}`。`workbuddy_credits::cached()` 改为 **内存 → 磁盘 → 空** 三级回落；`current_cache()` 读盘后顺手灌进内存，于是 `query_all(false)` 也能吃到上次运行的 5 分钟 TTL；`query_all` 算完**立刻 `persist_disk`** |
| **前端 store** | **新增** `src/lib/overview-store.ts` —— 模块级单例（`useSyncExternalStore`）。`primeOverview()` 读磁盘缓存，`refreshOverview()` 后台重算，`rememberReclaim()` 先更新内存再写回后端 |
| **预热时机** | ⚠️ **v0.0.18 已改**：原先在 `App` 根组件 `useEffect` 里调 `warmOverview()`，但 `useEffect` 是**子组件先于父组件**执行 —— 首页自己的 effect 先跑，它触发的两条重活把队列占住，缓存回包被压到后面。现在上移到 `main.tsx`，编排为 **prime → mount → refresh**（见 T17） |
| **可回收空间保鲜期** | 两侧扫描要递归统计 GB 级目录，是本页最贵的一步。`RECLAIM_TTL_MS = 30 分钟`：缓存里有 30 分钟内的结果就直接用，否则在**后台**重扫（`reclaimBusy` 只影响那一个数字的文案，不阻塞任何交互） |
| **缓存不覆盖实时结果** | `primeOverview()` 用 `state.overview ?? c.snapshot`（而不是直接赋值）：用户点过「刷新」之后再切回首页，不会被旧缓存盖回去 |
| **新增命令** | `app_overview_cached`、`app_overview_save_reclaim(traeBytes, wbBytes)`（v0.0.18 起均为 `async` + `off_main`，见 T17） |

### T17 · 修「启动后约 10 秒点不动界面」——重活不许压在主线程上（v0.0.18）

> 对应用户反馈：「这个界面预计卡了 10s 才能进行程序操作，没有解决缓存读取问题」。
> T16 的缓存本身是对的，但**症状没消**——因为卡顿根本不来自缓存读得慢。

| 字段 | 内容 |
| --- | --- |
| **真根因** | **Tauri 的同步命令跑在主线程上**（Windows 上那同时是 WebView2 的消息循环线程）。`trae_cleanup_scan` / `trae_wb_cleanup_scan` 都是 `pub fn` 同步命令，而首页一挂载就 `Promise.allSettled(ctx)` 并行触发两条 —— 它们在主线程上递归统计几 GB 目录，**窗口就是死的** |

| **修法①：统一出口** | `commands.rs` 新增 `async fn off_main<T, F>(f) -> Result<T, String>`（`spawn_blocking` 的薄包装 + 注释写清来龙去脉）。凡是碰**磁盘目录树 / SQLite / 进程枚举**的命令一律 `async` + `off_main` |

| **修法③：启动顺序前移** | 由 `App` 的 `useEffect` 上移到 **`main.tsx`**，编排成 **`primeOverview()` → 挂载 → `refreshOverview()`**：<br>① 先读缓存再挂载 ⇒ **首屏第一帧就是真实数据**（不再先闪一帧骨架屏）；<br>② `useEffect` 子先于父的问题消掉；<br>③ 加 `PRIME_TIMEOUT_MS = 800` 兜底 —— IPC 万一不回也照常挂载，不会把窗口停在启动占位上 |

| **判断标准（写进注释了）** | 命令体里**会不会递归读目录树 / 开 SQLite / 枚举进程** —— 会，就必须 `off_main` |
| **实测** | 总览重算 **3510 ms**（本来就在 `spawn_blocking` 上，无变化）；改造后三条重活仍要跑，但**界面全程可操作** |

### T19 · 修「Trae 账号卡排版错乱：姓名看不见、徽标一字一行」（v0.0.20）

> 代码读起来 `min-w-0 flex-1` 完全正确，渲染出来却是 0 宽。

| 字段 | 内容 |
| --- | --- |
| **现象** | Trae 账号卡上：账号名与 uid **整行消失**；`当前登录` / `网页凭证` 被压成**一字一行**的竖排；手机号 chip 横着**溢出卡片、盖住右上角按钮** |

### T21 · 修「workbuddy 清理失败：未能在 20 秒内退出」（v0.0.22）

> 用户原话：「workbuddy 清理失败」+ 清理页截图（报「WorkBuddy 未能在 20 秒内退出，已中止（未改动任何数据）」）。

| --- | --- |

| **修法 ②：区分「杀不掉」与「被重新拉起」** | 超时后看残留 PID：与**首轮完全不重叠** ⇒ `restarted = true`。给用户的话因此分成两句：被重启 ⇒「多半是它正在自动更新、或被更新器/守护进程拉了起来，请等它稳定后再试」；真杀不掉 ⇒「仍有 N 个进程没退出（PID …）；结束命令的返回：…」 |

| **真机验证（不碰 WorkBuddy）** | 新增 `cargo run -p wb-switch-core --example kill_tree_probe`：拿一个**隐藏窗口的 `ping` 当诱饵**，用后台线程每 200 ms 把它**复活**（模拟更新器）⇒ 实测 `ok=false attempts=6 restarted=true`，**正确识别为「被重新拉起」**；去掉复活线程 ⇒ `ok=true attempts=1`，一轮结束。两条分支都符合预期 |
| **测试** | `cargo test --workspace`：**152 + 2 全绿**（`process_list` 新增 5 条：树根挑选、`CmdResult` 摘要取 stderr、空匹配即返回 ok、`hint()` 两种文案）；`commands::main_thread_guard` 两条护栏仍过（本轮没加同步命令） |
| **验收** | `npx tsc --noEmit` 零错误；`npx vite build` 成功（609.99 KB JS / 73.10 KB CSS） |

### T24 · 自动更新（对接 GitHub Releases）（v0.2.0）

用户需求：「软件添加自动更新功能，对接 github」，并点名可参考 `_ref/workbuddy-switch-main`。

| 项 | 落点 |
| --- | --- |
| **整体方案** | 走 Tauri 官方 `tauri-plugin-updater` + `bundle.createUpdaterArtifacts` + GitHub Releases 里的 `latest.json` 资产。**不写自研更新器**：下载、签名校验、安装全在插件内部完成 |
| **版本检查（core）** | 新增 `crates/wb-switch-core/src/modules/update.rs`：`compare_versions` / `updater_manifest_urls` / `update_check`。**刻意不走 GitHub API**（60 次/小时/IP 限流）—— 主端点读 release 资产里的 `latest.json`，兜底端点读 `/releases/latest` 的 302 `Location` 头（**必须禁跟随重定向**，否则拉回来的是几十 KB 的发布页 HTML）。成功结果进程级缓存 6 小时，**失败不缓存** |
| **状态机（宿主）** | 新增 `src-tauri/src/update_service.rs`：`UpdatePhase{ Idle, Checking, UpToDate, Available, Downloading, ReadyToRestart, Error }` + `UpdateSnapshot`（含 `current`，供界面显示「v0.1.0 → v0.2.0」）。前端**只订阅 `update-state` 事件**，不自己调 JS 版 updater —— 状态只有一个真相源，不会出现「弹窗说 30%、侧栏说已最新」 |
| **命令** | `update_state`（同步，只读一个进程内互斥体，已登记 `SYNC_ALLOWLIST`）/ `update_check` / `update_download` / `update_restart`。四条都是薄包装，实现全在 `update_service` |
| **前端** | `src/lib/update.ts`（常量 + 打开发布页）、`src/lib/use-update-state.ts`（模块级单例订阅；首次订阅先 `update_state` 拉一次，兜住「检查在挂载前就完成」的时序）、`src/components/update-entry.tsx`（侧栏底部版本行 + 状态行 + 对话框）。**侧栏那行用 `grid-cols-[minmax(0,1fr)_auto]`，不用 `flex-wrap`**（T22 的教训）；状态行必须 `truncate` |
| **发布流水线** | 新增 `scripts/release.mjs`：带签名构建 → 生成 `latest.json` → 创建/复用 Release → 上传「安装包 + `.sig` + `latest.json`」。`package.json` 加 `build:signed`（只打包）与 `release`（打包 + 发布） |
| **检查时机** | 启动 **15 秒**后首检（不跟首屏抢资源），之后每 **30 分钟**一次；手动点刷新走 `force=true` 绕缓存。**下载完成不自动安装** —— 包先存内存，用户点「重启并安装」才落盘（Windows NSIS 要求应用先退出，自动装等于强制重启） |

**三条硬约束（改这块前必读）**：

1. **`TAURI_SIGNING_PRIVATE_KEY` 要的是「密钥内容」，不是路径。** `tauri signer generate` 的提示里
   虽然列了 `TAURI_SIGNING_PRIVATE_KEY_PATH`，但那个变量只有 `signer` 子命令认；`tauri build`
   用它会在**打包最后一步**才报「A public key has been found, but no private key」—— 白等一整轮编译。
2. **`latest.json` 的 `signature` 必须经 JSON 转义。** `.sig` 文件是**两行**（`untrusted comment:` +
   base64），用 shell heredoc 直接插值会写出**带裸换行的非法 JSON**；客户端只会安静地报
   「清单解析失败」，看不出是格式问题。所以清单由 `scripts/release.mjs` 用 `JSON.stringify` 生成并自检。
3. **每次发版都必须把 `latest.json` 传成 release 资产。** 客户端只认
   `releases/latest/download/latest.json`；少传这一份，老版本永远看不到新版。

**三个必须知道的运营事实**：

- **版本号每次只进一位补丁号**（`0.1.0 → 0.1.1 → 0.1.2`）—— 用户 2026-10-06 明确要求。
  **只有用户明确要求才跳次版本号**（如 `0.2.0`）。别自作主张把功能增量当次版本号的理由。
- **私钥即信任根**：`tauri.conf.json` 的 `plugins.updater.pubkey` 是唯一被接受的签名者。私钥丢了
  ⇒ 以后签不出老客户端认得的包 ⇒ 只能让用户手动重装。私钥在 `~/.twin-switch-keys/`（**仓库外**，
  `.gitignore` 已挡 `*.updater.key`），签发口令在同目录的 `.password`。
- **v0.1.0 的安装包没有更新能力**（那一版还没这个功能），所以**必须手动装一次 v0.2.0**；
  从 v0.2.0 起才能自动收到后续版本。

**另外三个踩到的坑**：

- **`npm run tauri build` 从此需要密钥**：`createUpdaterArtifacts` 一开，没有密钥的构建会在打包阶段
  失败。日常本地打包用 `npm run build:signed`。这条已写进 README。
- **版本号兜底串搬家了**：原来在 `src/App.tsx` 的侧栏版本行，现在跟着组件到了
  `src/components/update-entry.tsx`；`release.mjs` 的四处交叉核对也已跟着改。**「五处」现在是
  「四处 + Cargo.lock 自动跟上」**。
- **临时预览页的 Vite root 一换，Tailwind 就不再扫 `src/`**（本轮在做界面自检时踩到）：
  预览配置把 `root` 指到 `preview/` 之后，Tailwind v4 的自动源检测只扫 `preview/`，
  `grid-cols-[minmax(0,1fr)_auto]` 这类只在 `src/` 出现的类**压根没被生成** ——
  量出来的 `gridTemplateColumns` 只剩一列（`202px`）、按钮宽 202 px，**看着像组件布局崩了，
  其实是预览的 CSS 缺类**。修法：预览专用 CSS 里写 `@import "../src/index.css"; @source "../src";`。
  **判据：预览里的度量只要是「整齐地全不对」（比如按钮量满宽），先怀疑 CSS 没生成，再怀疑组件。**
- **沙箱会拦 vite 重建依赖缓存**：`node_modules/.vite/deps` 的批量删除会触发
  `SAFE_DELETE_BULK_CONFIRM_REQUIRED`，dev server 直接起不来。给预览配置单独设 `cacheDir`
  （如 `preview/.cache`）即可绕开。

**关键设计点**：

- **`client_key` 一并存进成员**：同名 uid 在不同客户端可能是不同人，关联判活必须限定在同一客户端内。
- **判活三条件**：存在 + 未软删 + **归属真的等于预期 uid**（只看 id 存在会把「会话已被改归属」误判成活着）。
- **时间字段字符串原样透传**（`updated` / `created`）：Trae 侧前端本来就 `{s.updated}` 直接展示，
  **不要自作主张转毫秒** —— 无时区的本地时间串按 UTC 解析会差 8 小时（本轮踩过，测试因此红过一次）。
- **`upsert_group` 复用已有组**：同一对 (源, 目标) 再次复制时只替换目标成员，不新建组，避免重复登记。

**顺带修掉的一个真 bug**：同库复制的 `CopyOpts.new_sid` 原为
`Some(native_hex_id())` **在循环外只调一次、整批共用**，导致多选复制时只有第一个会话成功，
其余被静默当作「已存在」跳过。改为按会话生成（`same_db_for` / `cross_db_for` 两个构造器，
`copy_session` 内 `None if same_db => native_hex_id()`），并**回传实际写入的 id** 供登记使用。
已补 3 条测试（多会话各自不同 id / 跨库保原 id / 同库复制已存在的被跳过），并做变异验证确认测试有效。

**界面自检踩到的两件事**（沿用 T24 的预览自检法）：

- **Radix Tabs 不认纯 DOM `.click()`**：`--screenshot` 一把梭时 Tab 切不过去，四张截图字节数完全相同。
  改用 **CDP 派发完整 `mouseMoved → mousePressed → mouseReleased` 序列**，并在读度量时**先校验
  `data-state="active"` 的表头**（会话记录 6 列 / 复制与关联 5 列），避免「截了但没切」的假通过。
- **⚠️ 别把 shadcn `<Table>` 的横向滚动当缺陷**：Table 组件**自带**
  `data-slot="table-container"`（`relative w-full overflow-x-auto`），窄窗口下 813 px 的表在 622 px
  容器里是**可滚动的**，不是被裁掉。判据：探针里 `scrollWidth > clientWidth` 即证明能滚；
  把容器 `scrollLeft = scrollWidth` 后操作列 `actInView: true` 即证明可达。

  `SAFE_DELETE_BULK_CONFIRM_REQUIRED`。
- **`Emulation.setDeviceMetricsOverride` 在 Edge headless 下不重排**：量出来的 `innerWidth`
  永远是首开值。要测多宽度就**每个尺寸单开一个 Edge 进程**给真实 `--window-size`。

### T28 · Trae 会话复制：全量重写 → 增量回写（v0.2.3）

用户反馈（附截图，进度日志停在「**加密回写 60416 / 80041 页**」）：
「**你进一步分析 trae 会话记录，是否单独会话的复制关联必须要解密全部并加密全部回写吗，这样速度太慢了**」。

**结论：不必，且现在的实现确实是 bug。** 逐行审 `import_sessions` 发现，一次「复制 3 个会话」
竟跑 **3 遍整库**（80041 页 / ~312 MB）：

| 环节 | 代码位置 | 开销 |
| --- | --- | --- |
| ① 解密目标库 → 明文副本 | `decrypt_database(&dst_db, …)` | 全量 80041 页 |
| ② 复制会话行 | `copy_session` | 只碰几页 ✅ |
| ③ **加密回写** | `encrypt_db_file()` ← **截图里那串日志** | **全量 80041 页** ❌ |
| ④ 再解密一遍自检 | `decrypt_database`（只为查一个 `count(*)`） | 全量 80041 页 ❌ |

**理论依据（SQLCipher 逐页独立加密）**：每页自带随机 IV + HMAC、**页号参与 HMAC**、页长恒 4096
⇒ **未变动的页沿用原密文天然合法**。唯一硬约束是**首页 salt 必须沿用原值**：
`mac_key = derive_mac_key(enc_key, salt)`，换 salt 会让所有未变动页的 HMAC 全部失效。

**最刺眼的一点**：同文件里**早就写好**了 `write_db_incremental()`（只重写变动页），带 2 条单测，
模块头注释第 13 行明写「第 3 步用 `write_db_incremental`（v0.0.6 起）」——
**文档写了、实现也有、单测也绿，但主流程根本没调用它**。这是真 bug，不是设计取舍。

**三处修复**：

| # | 位置 | 改法 |
| --- | --- | --- |
| ① | 第 4 步 | `encrypt_db_file` → **`write_db_incremental_with(&enc_key_hex, &dst_db, Some(&orig_plain), &plain, &new_db, …)`**：整库密文照抄 + **只重写真正变动的页**（实测几百页） |
| ② | 第 2 步 | 保留**原库明文** `target-orig.db`：`decrypt_database` 的输出目标改为它，再 `std::fs::copy` 一份 `plain` 给 SQLite 改。把它当 `old_plain` 传给 ① ⇒ **免掉增量函数内部「再解密一遍原密文做比对」**（否则解密要跑两遍）。多一次 312 MB 字节复制（~0.3–1 s），换掉 8 万页 AES 解密，划得来 |
| ③ | 第 6 步 | 「替换后整库再解密一遍，只为查一个 `count(*)`」→ **轻量自检**：新库大小 == 页数 × 4096 + 首页 HMAC 通过；会话数直接用复制阶段就有的 `sid_pairs.len()`（`verified_sessions`） |

**新增能力：`write_db_incremental_with(enc_key_hex, src_enc, old_plain: Option<&Path>, new_plain, out_path, on_progress)`**
—— `write_db_incremental` 变成它的薄封装（`old_plain = None`，退回逐页解密比对）。
有 `old_plain` 时直接字节比对（零解密）；没有时才在该页真解一次。**`old_plain` 必须与 `src_enc` 逐页一一对应**，否则比对结果无效。

**正确性由三层覆盖**（因此第 6 步才敢做轻量自检）：
① `write_db_incremental` 内**逐页回读解密比对**（写多少验多少）；
② 其收尾校验首页 HMAC + 输出大小 = 页数 × 4096；
③ 加密前用明文副本（就是回写的源头）核对会话数。

**预计效果**：3 遍整库（80041 × 3 页，分钟量级）→ **1 遍解密 + 1 遍字节复制 + 几百页加密回写**（秒级）。

| 校验 | 结果 |
| --- | --- |
| `cargo test` | **181 + 15 全绿，0 failed, 1 ignored**（较上轮 179 增 2 条新测试） |
| `npx tsc --noEmit` | 零错误（本轮前端零改动） |
| 新增测试 ① | `incremental_write_with_old_plain_matches_decrypt_path`：传 `old_plain` 的「快路径」与逐页解密的「慢路径」——**变动页数一致（= 2，第 5 页改动 + 第 21 页追加）**、**每页解密回明文逐页相等**、**未变动页逐字节复用原密文** |

**本轮踩的坑（最值钱的一条）**：

- **⚠️ 密文不可逐字节比较——SQLCipher 每页用随机 IV**：同一明文页两次加密得到**不同密文**（都合法、都能解回同一明文）。
  新测试最初断言「两条路径产出的密文逐字节相同」直接失败，暴露出这个语义。
  **判据必须是「解密回明文一致」**；**唯一能逐字节比的是未变动页**（它们直接沿用原密文）。
- **测试页数别数错**：`synth_plain(20, 11)` 生成 **20** 页，追加 `synth_page(21, 7)` 后共 **21** 页
  （86016 / 4096 = 21），一度写成 22 ⇒ `range end index 90112 out of range for slice of length 86016`。
  引入 `let total_pages = 21u64;` 并加 `assert_eq!(out_fast.len(), total_pages as usize * PAGE_SZ)` 兜住。
- **保留区检查看的是 `new_plain` 不是 `old_plain`**：中断测试最初把 bogus 明文当 `old_plain` 传，
  但函数检查的是**待回写的明文**的保留区，而它干净 ⇒ 不会报错。改为「`old_plain` 用干净原库明文 +
  `p_dirty` 第 3 页保留区塞 `0x7f`」⇒ 该页被判为变动 ⇒ 命中检查。
- **删全量自检别连带删掉它产出的变量**：删掉 `verified`（整库重解密数出来的会话数）后 JSON 返回还在用它
  ⇒ 编译失败 `cannot find value 'verified'`。改为 `verified_sessions = sid_pairs.len()`（复制阶段的真实落库数，等价且免费）。
- **`dst_conn.close()` 之前取数**：`plain_sessions`（`SELECT count(*)`）一度写在 `close()` 之后 ⇒ 编译期借用错误。
- **`use std::io::Read;`**：读新库首页做 HMAC 自检时 `read_exact` 找不到方法，需在块内补 trait 导入。
- **`cargo test` 的 `failed to write …\invoked.timestamp` 是已知 Windows 瞬时锁**（`os error 5` 的一类），
  **重跑即过**（`sleep 5` 后第二遍全绿）；别当成代码错误。

### T29 · 副本工程归属不一致 ⇒ Trae 客户端删不掉 / 重启复活（v0.2.4）

用户反馈：「**我重新测试发现新问题，我是从别的项目复制了会话过来，然后再 trae 里面操作删除，
其实是删除不掉的，重启 trae 发现记录会恢复**」。

**先说一个被排除的近似问题（T25 遗留的 UX 表象）**：上一轮用户报「删了还在」，排查后是
**两条标题 / 时间戳完全相同的副本**（rowid 34 / 35），删掉一条后另一条长得一模一样 ⇒ 误判。
那条**不是 bug**，只是列表没有「副本」标识。**本轮这条是真的**：客户端里点删除**没反应**，
重启后**原地复活**。

**根因（一句话）**：`copy_session` 里 `session_project` 的复制块**只改写了 `session_id`、
照抄源行的 `project_id`**，而 `chat_session.project_id` 已经被改成目标账号的新项目 ⇒ **两表打架**。

实测数据（`solo-cn` 库，副本 session_id `5bad8258…`）：

| 表 | 副本该行的 project_id | 归属 |
| --- | --- | --- |
| `chat_session` | `c81807b85bfee8b28d042160` | 目标账号（uid `925158341882023`）的新项目 ✅ |
| `session_project` | `6ac3a1a44de871d609c84147` | **源账号（uid `4052137095223728`）的旧项目** ❌ |

两个项目的计数也印证了错位：

| project_id | 该项目的 `chat_session` | 该项目的 `session_project` |
| --- | --- | --- |
| `c81807b8…`（新项目） | **1** | **0** |
| `6ac3a1a4…`（旧项目） | 1 | **2** |

**为什么这条链会「删不掉 + 复活」**：Trae 客户端**按 `session_project.project_id` 组织项目下的会话**。
副本的 `chat_session` 说自己属于新项目，可关联登记却挂在旧项目上 ⇒ 用户在**新项目**里点删除，
客户端按当前项目归属校验时**找不到这条关联** ⇒ 删除不生效；重启后客户端从 `chat_session`
重新加载列表 ⇒ **记录原地复活**。

**顺带发现的第二处同类错误**：`chat_session.context`（JSON 字符串）里的 `last_real_project_id`
同样**照抄源行** ⇒ 仍指向源账号的旧项目（甚至指向一条已被删除的项目记录）。
Trae 用它定位会话的「真实工程」，指向不存在的项目会触发客户端**自身的修复 / 重建逻辑**，
与上面的错位叠加，正是「删不掉 + 复活」的完整成因。

**排查覆盖面（确认没漏表）**：逐个数过带 `project_id` 的表 —— 只有 `chat_session` 与
`session_project` 有数据；`core_memory` / `snapshot` / `staging` **均 0 行** ⇒ 修复面完整。
另排查云端因素：`server_history_info` 对两条副本都是 **0 行**，且 `delete_cloud_session`
**只在有 oauth 凭证时才调** ⇒ **云端不是本次原因**，问题纯在本地库。

**四处修复**：

| # | 位置 | 改法 |
| --- | --- | --- |
| ① | `copy_session` 的 `session_project` 块 | 新增 `pid_idx` / `new_pid`，**同库复制时把 `project_id` 一起改写成 `dst_project_id`**，与 `chat_session` 对齐 |

### T30 · 关联记录增补：分叉检测 + 就地同步 + 提醒弹窗（v0.2.5）

用户提问：「**关联记录怎么用，我复制了一个会话，然后在新会话里面发起了新对话，切换账号后并没有提示
是否关联的弹窗，也没有自动更新另外一个会话记录**」。

**先判定这不是 bug，是功能没做**：核过三处代码，「关联」原先只做两件事 ——
① 在「复制到目标账号」成功时**自动登记**一个关联组；② 在表格里**巡检两端副本还在不在**
（`linked` / `targetMissing` / `sourceMissing` / `gone`）。**没有变化检测，也没有任何弹窗**
（全页只有会话详情弹窗与删除确认弹窗）。用户的两个期待都属未实现。

**本轮按用户要求的四项能力补齐**：

| # | 能力 | 落点 |
| --- | --- | --- |
| ① | **检测两端是否分叉** | `trae_session_links.rs` 新增纯函数 `divergence_of` |
| ② | **进入页面自动重新扫描** | `TraeRecordsPage.tsx` 已有 `useEffect`（`tab === "links"` 时 `loadLinks()`），本轮确认无需手动点刷新 |
| ③ | **一键同步差异** | `trae_import::sync_group` + `trae_session_sync_group` 命令 + 表格行内箭头按钮 |
| ④ | **弹窗提醒** | 关联数据加载完若发现分叉即弹一次，可「不再提示」（存 `localStorage`） |

**分叉判定规则（`divergence_of`，纯函数有 4 条单测）**：

判定优先级 —— **消息数是主判据，时间是次判据**：

| 情况 | 结果 |
| --- | --- |
| 任一端失效（会话没了 / 归属不符） | `unknown` —— **不按剩下一端推断** |
| 消息数读不到 | `unknown` |
| 消息数不同 | `sourceAhead` / `targetAhead`（条数多的靠前） |
| 消息数相同、`updated` 不同 | `sourceAhead` / `targetAhead`（定长串字典序即时间序） |
| 两者都相同 | `none`（未分叉） |

⚠️ **为什么「任一端失效」必须回 `unknown` 而不是按另一端猜**：这个字段会驱动界面上的
「可以同步」暗示，而同步是**会写库覆盖数据**的。猜错方向的代价是真丢内容，宁可不给建议。

**「同步差异」为什么不是「再复制一次」（`sync_group` 的核心设计）**：

普通复制（`import_sessions`）**永远新建 session id**，于是每次同步都会多出一条记录、关联组里
堆出一串副本。而「同步差异」的语义是**就地更新**：把陈旧那份的正文换成新的，**会话 id 保持不变**，
客户端里的位置、归属、关联登记全都不用动。

实现 = **删掉旧那条的全部行 + 以旧 id 重新写入新内容**，两步放在**同一次**解密 / 回写里完成，
所以不会出现「删掉了但没写上」的中间态。复用点：

- 删行复用 `trae_delete::delete_rows_in_conn`（**新增**，从 `delete_sessions_core` 抽出）：
  沿用 `classify_tables` 的「按列名找表」策略（带 `session_id` 或 `message_id` 的表全清），
  不写死表名 —— Trae 各版本表结构不一，写死必漏表。
- 写回复用 `copy_session` 的 `new_sid` 固定 id 分支（该分支原本只给单条复制路径用）。
- **覆盖后的归属取「被覆盖的那一端」的 uid**：同步只换内容，不该改变会话在账号间的归属。

安全链路与删除 / 导入严格一致：**结束客户端 → 整份备份 → 增量回写 → 校验 → 重启**；
替换失败回滚；备份进 `import_backup_dir()/…-sync-<ts>/`；顺带对齐工程归属（T29 的规则）。

### T31 · 跨账号同步修复 + 切号后分叉同步提示窗（v0.2.6）

用户报障 + 提需求：「**跨账号关联同步失败**。新增功能：当从 A 账号切换到 B 账号，当 2 个表之间

**① 同步失败 —— 真实数据坐实的根因（uid 角色写反）**

`sync_group` 的归属校验里，被覆盖一端（stale）比对的是**写死的另一个 uid**：

| direction | stale 端（被覆盖） | 实际归属 | 校验却取 | 结果 |
| --- | --- | --- | --- | --- |
| `sourceToTarget` | target 端 | `tgt_uid` | `src_uid` | 必然失配 |
| `targetToSource` | source 端 | `src_uid` | `tgt_uid` | 必然失配 |

（`CopyOpts.dst_uid` 取 `kept_uid`）**都从这里取值** —— 两边不可能再各写一套配错。

**② 批量同步（给切号弹窗铺路）**

direction)])`。为什么必须批：每个写库周期都要「退客户端 → 备份 → 增量回写 → 重启」，

### T32 · 跨账号同步后「客户端只剩一句」+ 同步写路径漏合并 WAL（v0.2.7）

用户报障：「**我在账号 B 新增对话后，点击关联同步到账号 A，切换到账号 A 之后，会话只剩一句了**，
排查原因并修复。」
现场（唯一那组关联）：源 `2908be72bbcf78fa054f6577`（uid `8426816007…`，8 条 / 4 轮）
→ 副本 `e60bf5c302083b0ad28baba2`（uid `4052137095…`，16 条 / 8 轮）。

**① 真根因：把「源 id 列表」和「`IN` 查询返回的行」按位置 zip —— 而这两个序列的顺序保证不同**

| 序列 | 怎么来的 | 实际顺序 |
| --- | --- | --- |
| `mids` | `SELECT message_id … WHERE session_id=?` | `session_id` 索引 ⇒ **rowid 序**（＝对话先后） |
| `rows` | `SELECT … WHERE message_id IN (…)` | 走 **`message_id` 索引 ⇒ 字母序** |

代码原本是 `mids.iter().zip(rows)` ⇒ 每条消息被写上的新 id **属于另一条源消息**。
`chat_turn.reply_to_message_id` / `response_message_id`（以及 `chat_message.reply_to_message_id`）
随后经 `mid_map` 改写，全部指向错人 ⇒ 客户端按「轮次」把 user ↔ assistant 配对渲染，
配对全部落空 ⇒ **整段塌成一句**（数据其实一条没少，是「引用关系」被搅乱了）。

**修法（结构性，不是改循环顺序）**：新 id **只由「行自带的 `message_id`」推导**（行怎么排都不影响映射），
并且**先建齐全量 `mid_map`、再统一改写会话内引用** —— 消息可能引用它**后面**的消息，
边遍历边查 `mid_map` 会漏掉当时还没生成的目标 id。

> **判据（写进约定）**：任何 `vec.iter().zip(rows)` 处，先确认两个序列的顺序来自**同一个保证**。
> 一方是「查询计划决定的索引序」、另一方是「rowid 序」时，二者没有任何理由一致。

回归护栏 `same_db_copy_aligns_message_ids_with_their_own_rows`：夹具刻意让 id 的**字母序与插入序完全相反**
（插入 `zzz,yyy,xxx,www`，字母序 `www<xxx<yyy<zzz`），一旦退回「按位置硬配」必然失败。
真实库只读演练 `cargo test -p wb-switch-core real_data_sync_rehearsal -- --ignored --nocapture`
（跑在用户真库的副本上，**实时库一个字节不动**）实测：**重放前错位 4 个 → 重放后 0 个**。

**② 同时坐实的第二个真 bug：同步写路径**漏了**合并 WAL —— 会把客户端刚写下的数据永久抹掉**

`sync_groups_inner` 的顺序是「解密目标库 → 改 → 校验 → 删 WAL/SHM」。
但 Trae 是 **WAL 模式**：客户端刚发出的消息很可能**还只在 `database.db-wal` 里**（尚未 checkpoint），
只解密主库 = 拿到一份**陈旧内容**，随后删 WAL 就把它们**永久抹掉**。
删除路径 `delete_sessions_core` 早就有这一步，**同步路径此前漏了**。

**修法**：第 4b 步在工作副本上补合并 —— `trae_delete::merge_wal_into_plain(&plain, &wal, &enc_key_hex)`；
合并页数 > 0 时**重新 `patch_reserved_field(&plain)`**（合并可能覆盖首页）。
⚠️ **只有工作副本 `plain` 合并，比对基准 `orig_plain` 保持「纯解密」** —— 它是增量回写的逐页比对基准，
必须与加密库的真实内容一一对应；只有 `plain` 带上 WAL 的新内容，那些页才会被判为「已变动」而重写进新库。

**③ 顺带查清一条会误导排查的读取陷阱（不属于本 bug）**

`reader_plain_path()` 只在**主库文件**签名（size/mtime/salt/header）变化时才刷新快照 ——
而 Trae 的写入几乎全在 WAL，主库字节往往纹丝不动 ⇒ **旧快照 + 新 WAL 合并出来的视图是坏的**。
`--example wal_merge_check` 四组对照实测：

| 组 | 做法 | `PRAGMA quick_check` |
| --- | --- | --- |
| A | 直接用 `reader_plain_path()` 视图（快照陈旧） | ✗ `... server_history_info ... database disk image is malformed` |
| B | 先 `ensure_decrypted` 刷新快照，再取视图 | ✓ `ok` |
| C | 现场复制「主库 + WAL」→ 解密 → 立刻合并 | ✓ `ok` |
| D | 旧快照副本 + 当前 WAL | ✗ `file is not a database` |

⇒ **判据**：任何排查脚本读 Trae 库前，先跑一次 `trae_export::ensure_decrypted()`
（`--example session_forensics` 已内置，可用 `FORENSICS_NO_REFRESH` 关掉做对照）。

### T33 · 导入 / 自愈路径删 WAL 前未合并 WAL：复制后客户端新写的内容被整段抹掉（v0.2.8）

**报障原文**：「trae 复制对话后，发起新内容，trae 无法正常响应，一直在思考，重启 trae 还是无法继续对话」。

**排障结论（分两半，别混）**

①「一直在思考」是 **Trae 云端 agent 针对某一个 conversation 卡死**，不是本地数据被写坏。
客户端日志显示每次卡住的发送都走完了本地流程：

```
sendMessage started → startStream entry → commitAndStartStream done
→ subscribeStream registered（subscriptionStatus: active）
→ MetadataHandler received metadata（status: in_progress）
→ ……之后再无任何内容事件（无 [sse-summary] plan item、无 [done]）
```

对照同一时段：源会话（12:01:32）与用户新建的会话（11:58:46）都是
`plan item first observed` → `[done] payloadStatus: completed`。
⇒ 服务端**收到了请求并且回了回执**，但那个 conversation 的云端 agent 不产出任何东西；
重启客户端当然无效（卡的是云端）。Trae 官方论坛这是长期存在的已知问题
（「对话卡死，一直在思考中，无法中断」），官方给的办法就是**换新会话**，或在**网页版**对该会话点「停止」
把云端那次运行终止掉。⇒ 该 conversation 只能弃用；重新复制会生成**新的 conversation_id**，那才恢复得回来。

**副本数据本身逐表核对过，是完整的**（所以不是我们写坏了）：

| 表 | 副本 | 结论 |
| --- | --- | --- |
| `chat_message` + `general`/`task` | 8 行 | 与源逐条内容一致（含同一 `task_id`） |
| `chat_turn` | 4 行 | `reply_to`/`response` 全部指向本会话自己的消息，无悬空 |
| `history_v2` | 25/25 | 复制时点的源侧行**一行不缺**（按 `created_at`+`content_source`+长度比对） |
| `session_project` / `project` | 各 1 行 | 指向目标账号自己的 project（`user_id` = A 账号） |
| `fts_message_content` / `fts_session_title` | ✓ | 词条照抄 |
| 跨会话重复 `message_id` / `agent_run_id` | 0 | 无碰撞 |

② **但确实找到了一个真实且严重的自身缺陷，而且日志把它坐实了 —— 就是本次修的东西：**
`import_sessions` / `heal_session_projects` **解密主库后直接改写、第 4 步再删掉 `-wal`，中间没有先合并 WAL**。
Trae 是 WAL 模式，客户端写下的消息可能长时间只在 `database.db-wal` 里、主库字节不变。
证据链（同一份日志 + 现在的库）：

- 11:44:51 发「你刚刚干了什么」→ 服务端 11:47:47 回了 **28144 token** 的正常答复；
- 11:47:40 再发 → 客户端 `[done] payloadStatus: completed`、`SessionStatusTrace` 3→5，**完整成功**；
- 这两轮在现在的库里 **`chat_message` / `chat_turn` / `history_v2` 里一条都不剩**，
  只在 `server_history_info` 留了 `hid/cid` 痕迹（`11:44:53 e60cc114`、`11:47:41 ef790e24`、`11:47:47 ef790f80`）；
- 中间只发生过一次整库回写：**11:49:06 的同步**（`import_backup/solo-cn-sync-20261007-114906`）。

⇒ 客户端刚写下、还没 checkpoint 的两轮内容，被我们那次「解密主库 → 改 → 删 WAL」永久抹掉了。
这正是「复制/同步之后，自己刚发的消息 / 刚回来的答复消失」的元凶。

**修法**：抽出共用助手，**解密明文后、任何改动前**先合并 WAL，挪了帧就重新打 reserved 字段。

```rust
/// 把实时库 WAL 里「已提交但还没 checkpoint」的帧并进明文副本。
/// ⚠️ 不做这一步，后续回写会删掉 WAL ⇒ 客户端刚写下、还没落盘的内容被永久抹掉。
fn merge_live_wal_into(plain: &Path, live: &Path, enc_key_hex: &str, log: &dyn Fn(&str)) -> Result<usize, String>
```

### T35 · 关联同步确认窗口前移到「账号切换之前」（v0.2.9）

**用户原话**：「关联记录同步应当在账号切换前就弹窗告知用户是否同步，而不是已经切换账号了在弹窗」

#### ① 问题

`TraeSwitchPage` 原先的顺序是 **先切、后问**：

```ts
const res = await api.traeSwitchTo(clientKey, entry.id);   // ← 账号已经换过去了
…
await probeDivergence(res.uid);                            // ← 这时才探测、才弹窗
```

用户看到提示时账号已经切完，**想反悔都来不及**；而且 `res.uid` 是切换**之后**才拿到的，
代码注释里也写明了「切过去了才问：此时才拿得到新账号的 uid」。

#### ② 为什么可以提前问（这是本任务成立的前提）

`trae_session_links::diverged_groups(client_key, uid)` **只读本地数据**（关联登记 +
实时库里的会话），`uid` 只是用来回答「**站在谁的角度看**」。它与
「客户端当前登的是谁」**完全无关** ⇒ 完全可以用**目标账号的 uid** 在切换前先探。

目标 uid 从账号库条目取：`entry.meta?.verified_uid ?? entry.oauth?.uid`。
**拿不到 uid 就不探测**（探测必须有一个「自己」）⇒ 不打扰，直接切。

#### ③ 新流程

```text
点「切换到这个账号」
  ├─ 目标账号有 uid？
  │    ├─ 否 → 直接切（静默，与以前一样）
  │    └─ 是 → 探测分叉
  │         ├─ count == 0 → 直接切（静默）
  │         └─ count > 0  → 弹「切换前确认」
  │                ├─ 取消切换          → 什么都不做
  │                ├─ 直接切换（不同步） → 执行切换
  │                └─ 同步 N 项并切换    → 同步成功后再执行切换
  └─ 切完之后**不再弹**（同一个问题不问两遍）
```

回滚（`onRollback`）走同一套：它同样是切换，没有理由少问一次；只有最后一步不同
（`runPending()` 一个出口分派 `doSwitch` / `doRollback`）。

**边界**：
- 探测失败 / 抛异常 ⇒ 返回 `null`，**绝不挡主流程**（切换是用户明确要的动作，提醒只是锦上添花）。
- 同步失败 ⇒ **停在原地**，`pendingSwitch` 保留，用户还能改选「直接切换」或重试。
  不能默默把切换做掉 —— 那等于绕过了他刚提的那个要求。

#### ④ 连带修掉的语义错位（**这是本任务最容易踩的坑**）

`DivergedRow` 原来的按钮写的是「同步到**当前账号**」/「同步到「对端」」，因为那时
「被探测的那一端」**一定**就是当前登录的账号。窗口前移之后这条前提**不再成立** ——
弹窗弹出时「当前账号」还是旧的那个，照旧文案会把方向**说反**，而这个动作是**覆盖数据**的。

**修法**：`DivergedRow` 里不再出现「当前账号」，两端一律用后端给的
`selfLabel` / `partnerLabel`（账号显示名）：
「同步到「用户3601675132」」/「同步到「用户8426816007」」。
自检提示也改成用账号名互相指代（`点「同步到「A」」，用「B」的内容重建这一份。`）。

#### ⑤ 渲染自查（改界面必做）

真组件 + 真事件（CDP 点真实的「切换到这个账号」按钮）跑 1600 / 1360 / 730 三档：

| 发现 | 处理 |

### T36 · Trae 会话记录补上「批量删除」（与 WorkBuddy 侧对齐）（v0.2.10）

**触发**：用户对比两端会话记录页 —— WorkBuddy 侧每行有勾选框 + 底部「删除所选」，
Trae 侧只能一条一条删（23 个会话就要点 23 次确认弹窗）。要求「trae 也要」。

#### 关键发现：批量能力后端早就有，只是没接出来

`trae_delete::delete_sessions(client_key, &[sid], log)` 早就存在（Trae 清理页在用它删空会话），
注释里写得很清楚：**整批只做一趟** —— 一次结束客户端、一次整库备份、一次解密、一次增量回写、
一次加密换回。而 `trae_delete_session`（单条）内部就是 `delete_sessions_core(&[sid])`。

所以前端逐条调用单删命令，等于把「整库备份 + 全库加解密」重复 N 遍，
**备份目录会按整库大小线性膨胀**（删 20 条 ≈ 20 份 250 MB 备份）。这是必须走批量命令的真正理由，
不只是少点几次。

#### 改动

| 层 | 改动 |
| --- | --- |
| `src-tauri/src/commands.rs` | 新增 `trae_delete_sessions(client_key, session_ids)`：去重保序 → **先解析全部归属 uid** → `trae_delete::delete_sessions` 一趟走完 → 再逐条尽力删云端任务列表记录 |
| `src-tauri/src/lib.rs` | 注册命令 |
| `src/lib/api.ts` / `trae-types.ts` | `traeDeleteSessions()` + `TraeBatchDeleteReport`（含 `cloud.{deleted,failed,skipped}`） |
| `src/pages/TraeRecordsPage.tsx` | 勾选列 + 表头全选 + 底部批量条 + 删除弹窗改为「1 条走预检 / 多条走整批说明」 |
| `src/pages/WorkbuddyRecordsPage.tsx` | 补表头全选（原来只能一行行勾，两端保持一致） |

#### ⚠️ 归属账号必须**先于**本地删除解析

```rust
let owners: Vec<(String, Option<String>)> = uniq.iter()
    .map(|sid| (sid.clone(), trae_import::session_owner_uid(&client_key, sid)))
    .collect();          // ← 必须在 delete_sessions 之前
```

本地删除会同步清掉解密库里的会话行；删完再查 `session_project → project.user_id` 就查不到归属，
云端任务列表里那些记录会**永久残留**。单条删除路径本来就是这样做的（`trae_delete_session`
第一行就是解析 uid），批量照抄。

#### ⚠️ 勾选与「可见行」是两件事

账号筛选会把一部分勾中的行藏起来。所以：

- 表头「全选」只作用于**当前可见**的行；
- **切换账号筛选 / 切换客户端一律清空勾选**（`useEffect(..., [clientKey, ownerFilter])`）——
  否则用户会在看不见那些行的情况下把它们删掉；
- 底部条在「勾选数 > 可见勾选数」时显式提示「另有 N 个被当前筛选藏起，已忽略」；
- 列表刷新后把已不存在的 id 从勾选里摘掉。

#### 弹窗设计

| 场景 | 内容 |
| --- | --- |
| 单条 | 保持原样：`trae_delete_info` 逐表预检 + 云端凭证判断 |
| 多条 | 会话数 / 正文合计 / 按归属账号分组徽章 / 待删标题清单 + 「整批一次完成：只解密一趟、只回写一趟、只留一份整库备份」 |

`openDelete(targets[])` 是唯一入口，`confirmDelete()` 按长度分支；预检只对单条做
（N 条就是 N 次读库，而批量本来就不需要逐条预检）。
批量结果不再塞进弹窗（弹窗一做完就关，放里面等于看不见），改为会话列表下方一张
「上次批量删除结果」卡片（与 WorkBuddy 同款留存）。

### T37 · 首页 Trae 卡片改为「按客户端独立」展示账号库 / 会话 / 积分（v0.2.10）

**触发**：用户指出首页里 WorkBuddy 侧有登录状态、账号库、会话、积分，Trae 侧只有一行
`● 13 个进程 · 3 个账号 · 未解密`。并明确要求：**「trea 不用客户端添加一个小标签来切换，
不要互相影响。不同客户端的会话独立」**。

#### 那条要求怎么落到代码上

Trae 的 4 个客户端各自有独立的 `%APPDATA%\<userData>\ModularData\ai-agent\database.db`、
独立的解密快照、独立的账号库（`vault_root()/<clientKey>/...`）。所以：

- **不做**客户端切换标签，而是**每个已安装客户端渲染一块**，块内自己一套
  「登录状态 / 账号库 / 会话 / 解密库 / 客户端路径 / 积分」；
- 每一块的数字**只从它自己的 key 算**：`trae_vault::list_vault_accounts(key)`、
  `read_snapshot_meta(key)` 的 `chat_session` 行数、`trae_credits::cached(Some(key))`；
- 卡片副标题写明「每个客户端的账号库与会话库各自独立」，把这件事告诉用户而不是只做对；
- 顶部「会话总数」仍是合计，但副标题改成「Trae 已解密客户端 30 · WorkBuddy 8」——
  没解密时明确写「Trae 未解密」，不再显示一个会被误读成「Trae 有 0 个会话」的 0。

#### 后端补的三块数据（`app_overview.rs`）

| 字段 | 来源 | 成本 |
| --- | --- | --- |
| `clients[].loginLabel` | `trae_discover::storage_json_path` → `trae_vault::uid_from_storage_text` → `account_label` | 两个几 KB 的 JSON，未登录直接跳过 |
| `clients[].credits` | `trae_credits::cached(Some(key))` 的 summary（**不联网**） | 读各账号 `profile.json` |
| `trae.topPick` | `client_usage::snapshot_for(&keys)["topPick"]` | 读一个使用记忆文件 |

⚠️ `credits` 是**压缩过的摘要**（`accountCount/queryable/withData/totalRemaining/updatedAt`），
不带逐账号明细 —— 否则总览缓存文件会被撑大。有单测钉住这一点。

⚠️ `topPick` 复用 `client_usage` 的唯一出口，**不在首页另算一遍「谁最常用」**：
同一件事被推导两次必然有一天会不一致（T34 的 `order_keys` 原则）。

⚠️ **`CACHE_VERSION` 1 → 2**：总览字段变了，旧缓存必须整份作废，
否则前端会读到「有 `trae` 但没有 `clients[].credits`」的半新半旧对象。

#### 前端

- `OverviewTraeClient` 增 `loginLabel` / `credits`，`Overview.trae` 增 `topPick`；
- 抽出 `TraeClientBlock` 局部组件，`Row` 复用 WorkBuddy 侧那套；
- 每个客户端自带「查询积分」按钮，只查**这一个**客户端的账号库
  （`traeCreditsQuery(key, true)`），与其它客户端互不影响；
- 查完**不自己拼一份摘要**，而是 `refreshOverview()` 重算 —— 摘要的唯一出口在后端。

#### 渲染自查（1600 / 1360 / 730）

| 发现 | 处理 |
| --- | --- |
| Trae 卡片从 ~220px 涨到 ~700px（3 个客户端），默认 `grid` 的 `stretch` 把 WorkBuddy 卡片拉成同高，中间留一大块空白 | 双栏网格加 **`items-start`**：卡片各按内容高度，不再强行等高 |

## 6. 常见操作步骤

### 6.1 新增一个「数据迁移 / 本机维护」页面

1. `src/pages/XxxPage.tsx`（照 `WorkbuddyCleanupPage.tsx` 抄结构：Card + 扫描 + 勾选 + 确认弹窗 + 进度 + 结果）。
2. `src/lib/api.ts` 加 `call("命令名", {...})` 封装；`src/lib/trae-types.ts` 加类型。
3. `src-tauri/src/commands.rs` 加 `#[tauri::command]`；写库/耗时命令用 `tauri::async_runtime::spawn_blocking`。
4. `src-tauri/src/lib.rs` 的 `invoke_handler` 里注册。
5. `src/App.tsx`：`SidebarLink` + `<Route>`；分区标题用现有的小标题 + 分隔线写法。
6. 进度事件命名 `trae-xxx-progress`，前端 `listen` 必须带 `active` 标记（React StrictMode 下异步注册有竞态，会重复投递）。

### 6.2 修改 WorkBuddy 的写行为

先读 `workbuddy_export.rs` 的「三条设计约束」与 `workbuddy_cleanup.rs` 的「安全约束」注释块，
它们记录了踩过的坑（整份替换 vs 增量、先正文后数据库、同步映射要一起清…）。

### 6.3 排查「某个会话为什么不显示」

按顺序看：①`~/.workbuddy/projects/` 下有没有 `{id}.jsonl`（无正文就在列表里显示「无正文」且选不中）；
②`sessions` 表里 `deleted_at` 是否非空（前端默认不显示已删除）；
③`workbuddy_source::list_sessions()` 是不是报错（数据根/库文件缺失）；
④**导入后「过程看不到 / 工具卡片不显示 / 参数是一坨转义 JSON」**：先跑
`cargo test -p wb-switch-core -- --ignored real_plan_item_shape --nocapture`，它会把本机真实会话过一遍并断言 `plan_item` 字段齐备。若失败，多半是 `workbuddy_source.rs` 里某个事件字段又被多包了一层（参见 T5 的「双重编码」）。
