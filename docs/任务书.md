## 1. 项目概况

| 项 | 内容 |
| --- | --- |
| 名称 | **TwinSwitch · 双栖**（v0.0.24 起；原名 trae-switch-cn。Tauri 2 + React 19 + TypeScript + Rust） |
| 工作目录 | `D:\htw\签到\trae-switch-cn` |
| 核心库 | `crates/wb-switch-core`（不依赖 Tauri，可被 CLI/测试复用） |
| 桌面壳 | `src-tauri`（`commands.rs` 命令层 + `lib.rs` 注册表） |
| 前端 | `src/`（`pages/` 页面、`components/` 组件、`lib/api.ts` 调用封装、`lib/trae-types.ts` 类型） |
| 工作数据 | `~/.twin-switch/`（解密快照、备份、回收站都在这里） |
| 目标数据 A | Trae 客户端数据（SQLCipher 4 加密库） |
| 目标数据 B | WorkBuddy 数据（`~/.workbuddy/`，明文 JSONL + SQLite） |

### 1.1 两条迁移链路

```
WorkBuddy  ──(导出 JSONL + 插 sessions 行)──►  Trae 加密库      入口 /workbuddy-import
Trae 加密库 ──(读快照 + 转换)──────────────►  WorkBuddy 明文库   入口 /workbuddy-export
WorkBuddy 本机残留 ──(扫描 + 受控清除)─────►  回收站 / 彻底删除    入口 /workbuddy-cleanup
```

### 1.2 关键路径与常量

| 用途 | 位置 |
| --- | --- |
| 工具工作目录 | `~/.twin-switch/`（`config::store_dir()`） |

### T1 · 账号显示名（谁是谁）

| 字段 | 内容 |
| --- | --- |
| **状态** | ✅ 已实现，待真机确认显示效果 |
| **问题** | 界面上一律显示 `uid …97eac1`，多账号（本机 3 个）时完全分不清谁是谁 |
| **调研结论** | WorkBuddy **没有**本地账号表。可用的三个来源（可信度由低到高）：①`logs/*.log` 里的遥测行 `"userId":"…","username":"…","userNickname":"…"`（覆盖最全，但会被日志轮转清掉）；②`~/.wb-switch/accounts.json`（含手机号，装了才有）；③`storage/skeleton/account-snapshot.json`（WorkBuddy 自己写的，**只覆盖当前登录账号**） |
| **本机实测结果** | `…97eac1`→`13780001455`（当前登录，免费版）· `…be81ba`→`弦ྂ思ྂ`（手机 18858464309）· `…5d5e70`→`19550125362` |
| **设计** | 新增 `workbuddy_accounts.rs`：三来源按可信度依次合并（非空字段覆盖）、`label()` = `昵称（uid …尾6）`、`meta()` = `手机号 · 个人版 · 免费版`（自动去掉与显示名重复的部分）；**只读 uid/昵称/手机号/邮箱/类型/版本，绝不读 token**；`{nickname:{$wbEncrypted:…}}` 这类加密信封对象一律忽略（否则会把对象当字符串透传导致前端白屏） |
| **改动文件** | 新增 `crates/wb-switch-core/src/modules/workbuddy_accounts.rs`；`workbuddy_export.rs`（`target_info` 输出 `name/meta/kind/edition/name_source`，`target_label` 改用 `label_for()`）；`workbuddy_import.rs`（`list_source_sessions` 增加 `accounts` 数组）；`workbuddy-import-card.tsx`（按 uid 查表显示）；`WorkbuddyExportPage.tsx`（主行给名字、副行给 uid 尾号+版本+会话数） |

### T3 · 本机清理（扫描 + 受控清除）

| 字段 | 内容 |
| --- | --- |
| **状态** | ✅ 已实现，**未在本机执行过清除**（见下方「为什么没代跑」） |

| **安全约束（逐条对应实现）** | ①`scan()` 只用只读连接 + 遍历，绝不写；②清除前先退出 WorkBuddy（否则改库会被客户端内存快照覆盖）；③改库前整份备份 `workbuddy.db` 与 `edge-sync-mapping-v*.db`（含 WAL/SHM）；④文件默认**移入工具回收站**保持相对路径、可搬回，只有勾「彻底删除」才 unlink；⑤同步映射表一起清；⑥确认弹窗逐条列出将被处理的路径，彻底删除前用**加粗红字**警告不可逆 |
| **本机实测（只读扫描）** | 39 项 / **542.4 MB**，其中推荐清理 24 项 / 185.9 MB；大头：`logs/sandbox` 210.7 MB、`logs/2026-09-27` 80.7 MB；占用实测 `workspace` 2.74 GB（当前会话在用，**勿清**）、`binaries` 483 MB、`logs` 478 MB、`plugins` 128 MB、`traces` 88 MB |
| **改动文件** | 新增 `crates/wb-switch-core/src/modules/workbuddy_cleanup.rs`；`workbuddy_export.rs`（`wb_kill_all`/`wb_wait_stopped`/`wb_launch`/`open_wb_db_ro` 提升为 `pub(crate)` 复用）；`commands.rs` + `lib.rs`（`trae_wb_cleanup_scan` / `_purge` / `_empty_trash`）；`api.ts` + `trae-types.ts`；新增 `src/pages/WorkbuddyCleanupPage.tsx`；`App.tsx`（侧栏新增「本机维护」区 + 路由 `/workbuddy-cleanup`） |

| **验收** | `cargo test -p wb-switch-core`（含 `purge_db_rows_skips_missing_table`、`copy_dir_copies_recursively`）；`wb_audit` 第 3 节；真机：在 TwinSwitch 里点「WorkBuddy 清理」→ 扫描 → 勾推荐项 → 清理到回收站 → 打开 WorkBuddy 确认列表变干净 |

### T5 · 修复「详细过程在 Trae 里显示异常」（v0.0.11）

| 字段 | 内容 |
| --- | --- |
| **用户反馈** | 导出到 Trae 的会话，WorkBuddy 里看到的工具调用 / 思考过程，在 Trae 里显示奇怪（工具卡片不见、参数不成形） |

### T16 · 启动缓存：先读缓存 → 后台刷新 → 写回缓存（v0.0.17）

> 对应用户需求：「启动较慢，首页要加载很多信息，加载期间无法操作。你设置一个缓存，启动先读缓存，然后后台自动更新信息，更新后的信息实时写入缓存，方便后期加速启动」。

| 字段 | 内容 |
| --- | --- |
| **根因** | 首页原来在**组件挂载时** `await app_overview_snapshot()`。这个调用要枚举进程（WMI，几百 ms～数秒）+ 统计 SQLite + 递归数会话正文；期间整页骨架屏，**点不了任何东西**。而且数据只活在内存里，进程退出就没了 —— 每次冷启动都要重跑一遍 |
| **缓存落点** | `~/.twin-switch/cache/`（**新增** `config::cache_dir()`）。刻意与 `store_dir()` 分开：`store_dir` 存用户资产（账号库 / 回收站 / 解密快照），`cache` 只存**可再生的派生数据**（总览、积分），删掉只是变慢不会出错 |
| **通用读写助手** | `config::write_cache_json(name, &value)` / `read_cache_json(name) -> Option<Value>`（自动建目录；写走 `atomic_write`；失败只 `eprintln` 不影响主流程） |
| **总览缓存** | `cache/overview.json` = `{version, generatedAt, snapshot, reclaim}`。`CACHE_VERSION` 一改即视旧缓存为不存在，避免前端读到半新半旧的对象 |
| **三个新入口** | ① `app_overview::cached()` —— **只读文件不重算**，返回 `{ok, empty, generatedAt, ageMs, snapshot, reclaim}`；② `snapshot()` —— 算完**立刻写回**（保留上一份 `reclaim`）；③ `app_overview::save_reclaim(trae, wb)` —— 把前端并行扫出的可回收空间并进缓存 |
| **积分缓存** | `cache/credits.json` = `{version, at, items, errors}`。`workbuddy_credits::cached()` 改为 **内存 → 磁盘 → 空** 三级回落；`current_cache()` 读盘后顺手灌进内存，于是 `query_all(false)` 也能吃到上次运行的 5 分钟 TTL；`query_all` 算完**立刻 `persist_disk`** |
| **前端 store** | **新增** `src/lib/overview-store.ts` —— 模块级单例（`useSyncExternalStore`）。`primeOverview()` 读磁盘缓存，`refreshOverview()` 后台重算，`rememberReclaim()` 先更新内存再写回后端 |
| **预热时机** | ⚠️ **v0.0.18 已改**：原先在 `App` 根组件 `useEffect` 里调 `warmOverview()`，但 `useEffect` 是**子组件先于父组件**执行 —— 首页自己的 effect 先跑，它触发的两条重活把队列占住，缓存回包被压到后面。现在上移到 `main.tsx`，编排为 **prime → mount → refresh**（见 T17） |
| **可回收空间保鲜期** | 两侧扫描要递归统计 GB 级目录，是本页最贵的一步。`RECLAIM_TTL_MS = 30 分钟`：缓存里有 30 分钟内的结果就直接用，否则在**后台**重扫（`reclaimBusy` 只影响那一个数字的文案，不阻塞任何交互） |
| **缓存不覆盖实时结果** | `primeOverview()` 用 `state.overview ?? c.snapshot`（而不是直接赋值）：用户点过「刷新」之后再切回首页，不会被旧缓存盖回去 |
| **新增命令** | `app_overview_cached`、`app_overview_save_reclaim(traeBytes, wbBytes)`（v0.0.18 起均为 `async` + `off_main`，见 T17） |

### T17 · 修「启动后约 10 秒点不动界面」——重活不许压在主线程上（v0.0.18）

> 对应用户反馈：「这个界面预计卡了 10s 才能进行程序操作，没有解决缓存读取问题」。
> T16 的缓存本身是对的，但**症状没消**——因为卡顿根本不来自缓存读得慢。

| 字段 | 内容 |
| --- | --- |
| **真根因** | **Tauri 的同步命令跑在主线程上**（Windows 上那同时是 WebView2 的消息循环线程）。`trae_cleanup_scan` / `trae_wb_cleanup_scan` 都是 `pub fn` 同步命令，而首页一挂载就 `Promise.allSettled(ctx)` 并行触发两条 —— 它们在主线程上递归统计几 GB 目录，**窗口就是死的** |

| **修法①：统一出口** | `commands.rs` 新增 `async fn off_main<T, F>(f) -> Result<T, String>`（`spawn_blocking` 的薄包装 + 注释写清来龙去脉）。凡是碰**磁盘目录树 / SQLite / 进程枚举**的命令一律 `async` + `off_main` |

| **修法③：启动顺序前移** | 由 `App` 的 `useEffect` 上移到 **`main.tsx`**，编排成 **`primeOverview()` → 挂载 → `refreshOverview()`**：<br>① 先读缓存再挂载 ⇒ **首屏第一帧就是真实数据**（不再先闪一帧骨架屏）；<br>② `useEffect` 子先于父的问题消掉；<br>③ 加 `PRIME_TIMEOUT_MS = 800` 兜底 —— IPC 万一不回也照常挂载，不会把窗口停在启动占位上 |

| **判断标准（写进注释了）** | 命令体里**会不会递归读目录树 / 开 SQLite / 枚举进程** —— 会，就必须 `off_main` |
| **实测** | 总览重算 **3510 ms**（本来就在 `spawn_blocking` 上，无变化）；改造后三条重活仍要跑，但**界面全程可操作** |

### T19 · 修「Trae 账号卡排版错乱：姓名看不见、徽标一字一行」（v0.0.20）

> 代码读起来 `min-w-0 flex-1` 完全正确，渲染出来却是 0 宽。

| 字段 | 内容 |
| --- | --- |
| **现象** | Trae 账号卡上：账号名与 uid **整行消失**；`当前登录` / `网页凭证` 被压成**一字一行**的竖排；手机号 chip 横着**溢出卡片、盖住右上角按钮** |

### T21 · 修「workbuddy 清理失败：未能在 20 秒内退出」（v0.0.22）

> 用户原话：「workbuddy 清理失败」+ 清理页截图（报「WorkBuddy 未能在 20 秒内退出，已中止（未改动任何数据）」）。

| --- | --- |

| **修法 ②：区分「杀不掉」与「被重新拉起」** | 超时后看残留 PID：与**首轮完全不重叠** ⇒ `restarted = true`。给用户的话因此分成两句：被重启 ⇒「多半是它正在自动更新、或被更新器/守护进程拉了起来，请等它稳定后再试」；真杀不掉 ⇒「仍有 N 个进程没退出（PID …）；结束命令的返回：…」 |

| **真机验证（不碰 WorkBuddy）** | 新增 `cargo run -p wb-switch-core --example kill_tree_probe`：拿一个**隐藏窗口的 `ping` 当诱饵**，用后台线程每 200 ms 把它**复活**（模拟更新器）⇒ 实测 `ok=false attempts=6 restarted=true`，**正确识别为「被重新拉起」**；去掉复活线程 ⇒ `ok=true attempts=1`，一轮结束。两条分支都符合预期 |
| **测试** | `cargo test --workspace`：**152 + 2 全绿**（`process_list` 新增 5 条：树根挑选、`CmdResult` 摘要取 stderr、空匹配即返回 ok、`hint()` 两种文案）；`commands::main_thread_guard` 两条护栏仍过（本轮没加同步命令） |
| **验收** | `npx tsc --noEmit` 零错误；`npx vite build` 成功（609.99 KB JS / 73.10 KB CSS） |

### T24 · 自动更新（对接 GitHub Releases）（v0.2.0）

用户需求：「软件添加自动更新功能，对接 github」，并点名可参考 `_ref/workbuddy-switch-main`。

| 项 | 落点 |
| --- | --- |
| **整体方案** | 走 Tauri 官方 `tauri-plugin-updater` + `bundle.createUpdaterArtifacts` + GitHub Releases 里的 `latest.json` 资产。**不写自研更新器**：下载、签名校验、安装全在插件内部完成 |
| **版本检查（core）** | 新增 `crates/wb-switch-core/src/modules/update.rs`：`compare_versions` / `updater_manifest_urls` / `update_check`。**刻意不走 GitHub API**（60 次/小时/IP 限流）—— 主端点读 release 资产里的 `latest.json`，兜底端点读 `/releases/latest` 的 302 `Location` 头（**必须禁跟随重定向**，否则拉回来的是几十 KB 的发布页 HTML）。成功结果进程级缓存 6 小时，**失败不缓存** |
| **状态机（宿主）** | 新增 `src-tauri/src/update_service.rs`：`UpdatePhase{ Idle, Checking, UpToDate, Available, Downloading, ReadyToRestart, Error }` + `UpdateSnapshot`（含 `current`，供界面显示「v0.1.0 → v0.2.0」）。前端**只订阅 `update-state` 事件**，不自己调 JS 版 updater —— 状态只有一个真相源，不会出现「弹窗说 30%、侧栏说已最新」 |
| **命令** | `update_state`（同步，只读一个进程内互斥体，已登记 `SYNC_ALLOWLIST`）/ `update_check` / `update_download` / `update_restart`。四条都是薄包装，实现全在 `update_service` |
| **前端** | `src/lib/update.ts`（常量 + 打开发布页）、`src/lib/use-update-state.ts`（模块级单例订阅；首次订阅先 `update_state` 拉一次，兜住「检查在挂载前就完成」的时序）、`src/components/update-entry.tsx`（侧栏底部版本行 + 状态行 + 对话框）。**侧栏那行用 `grid-cols-[minmax(0,1fr)_auto]`，不用 `flex-wrap`**（T22 的教训）；状态行必须 `truncate` |
| **发布流水线** | 新增 `scripts/release.mjs`：带签名构建 → 生成 `latest.json` → 创建/复用 Release → 上传「安装包 + `.sig` + `latest.json`」。`package.json` 加 `build:signed`（只打包）与 `release`（打包 + 发布） |
| **检查时机** | 启动 **15 秒**后首检（不跟首屏抢资源），之后每 **30 分钟**一次；手动点刷新走 `force=true` 绕缓存。**下载完成不自动安装** —— 包先存内存，用户点「重启并安装」才落盘（Windows NSIS 要求应用先退出，自动装等于强制重启） |

**三条硬约束（改这块前必读）**：

1. **`TAURI_SIGNING_PRIVATE_KEY` 要的是「密钥内容」，不是路径。** `tauri signer generate` 的提示里
   虽然列了 `TAURI_SIGNING_PRIVATE_KEY_PATH`，但那个变量只有 `signer` 子命令认；`tauri build`
   用它会在**打包最后一步**才报「A public key has been found, but no private key」—— 白等一整轮编译。
2. **`latest.json` 的 `signature` 必须经 JSON 转义。** `.sig` 文件是**两行**（`untrusted comment:` +
   base64），用 shell heredoc 直接插值会写出**带裸换行的非法 JSON**；客户端只会安静地报
   「清单解析失败」，看不出是格式问题。所以清单由 `scripts/release.mjs` 用 `JSON.stringify` 生成并自检。
3. **每次发版都必须把 `latest.json` 传成 release 资产。** 客户端只认
   `releases/latest/download/latest.json`；少传这一份，老版本永远看不到新版。

**三个必须知道的运营事实**：

- **版本号每次只进一位补丁号**（`0.1.0 → 0.1.1 → 0.1.2`）—— 用户 2026-10-06 明确要求。
  **只有用户明确要求才跳次版本号**（如 `0.2.0`）。别自作主张把功能增量当次版本号的理由。
- **私钥即信任根**：`tauri.conf.json` 的 `plugins.updater.pubkey` 是唯一被接受的签名者。私钥丢了
  ⇒ 以后签不出老客户端认得的包 ⇒ 只能让用户手动重装。私钥在 `~/.twin-switch-keys/`（**仓库外**，
  `.gitignore` 已挡 `*.updater.key`），签发口令在同目录的 `.password`。
- **v0.1.0 的安装包没有更新能力**（那一版还没这个功能），所以**必须手动装一次 v0.2.0**；
  从 v0.2.0 起才能自动收到后续版本。

**另外三个踩到的坑**：

- **`npm run tauri build` 从此需要密钥**：`createUpdaterArtifacts` 一开，没有密钥的构建会在打包阶段
  失败。日常本地打包用 `npm run build:signed`。这条已写进 README。
- **版本号兜底串搬家了**：原来在 `src/App.tsx` 的侧栏版本行，现在跟着组件到了
  `src/components/update-entry.tsx`；`release.mjs` 的四处交叉核对也已跟着改。**「五处」现在是
  「四处 + Cargo.lock 自动跟上」**。
- **临时预览页的 Vite root 一换，Tailwind 就不再扫 `src/`**（本轮在做界面自检时踩到）：
  预览配置把 `root` 指到 `preview/` 之后，Tailwind v4 的自动源检测只扫 `preview/`，
  `grid-cols-[minmax(0,1fr)_auto]` 这类只在 `src/` 出现的类**压根没被生成** ——
  量出来的 `gridTemplateColumns` 只剩一列（`202px`）、按钮宽 202 px，**看着像组件布局崩了，
  其实是预览的 CSS 缺类**。修法：预览专用 CSS 里写 `@import "../src/index.css"; @source "../src";`。
  **判据：预览里的度量只要是「整齐地全不对」（比如按钮量满宽），先怀疑 CSS 没生成，再怀疑组件。**
- **沙箱会拦 vite 重建依赖缓存**：`node_modules/.vite/deps` 的批量删除会触发
  `SAFE_DELETE_BULK_CONFIRM_REQUIRED`，dev server 直接起不来。给预览配置单独设 `cacheDir`
  （如 `preview/.cache`）即可绕开。

## 6. 常见操作步骤

### 6.1 新增一个「数据迁移 / 本机维护」页面

1. `src/pages/XxxPage.tsx`（照 `WorkbuddyCleanupPage.tsx` 抄结构：Card + 扫描 + 勾选 + 确认弹窗 + 进度 + 结果）。
2. `src/lib/api.ts` 加 `call("命令名", {...})` 封装；`src/lib/trae-types.ts` 加类型。
3. `src-tauri/src/commands.rs` 加 `#[tauri::command]`；写库/耗时命令用 `tauri::async_runtime::spawn_blocking`。
4. `src-tauri/src/lib.rs` 的 `invoke_handler` 里注册。
5. `src/App.tsx`：`SidebarLink` + `<Route>`；分区标题用现有的小标题 + 分隔线写法。
6. 进度事件命名 `trae-xxx-progress`，前端 `listen` 必须带 `active` 标记（React StrictMode 下异步注册有竞态，会重复投递）。

### 6.2 修改 WorkBuddy 的写行为

先读 `workbuddy_export.rs` 的「三条设计约束」与 `workbuddy_cleanup.rs` 的「安全约束」注释块，
它们记录了踩过的坑（整份替换 vs 增量、先正文后数据库、同步映射要一起清…）。

### 6.3 排查「某个会话为什么不显示」

按顺序看：①`~/.workbuddy/projects/` 下有没有 `{id}.jsonl`（无正文就在列表里显示「无正文」且选不中）；
②`sessions` 表里 `deleted_at` 是否非空（前端默认不显示已删除）；
③`workbuddy_source::list_sessions()` 是不是报错（数据根/库文件缺失）；
④**导入后「过程看不到 / 工具卡片不显示 / 参数是一坨转义 JSON」**：先跑
`cargo test -p wb-switch-core -- --ignored real_plan_item_shape --nocapture`，它会把本机真实会话过一遍并断言 `plan_item` 字段齐备。若失败，多半是 `workbuddy_source.rs` 里某个事件字段又被多包了一层（参见 T5 的「双重编码」）。
